# Лабораторная работа 1. Оценка защищённости разработанного приложения

## 1. Постановка задачи

Разработать консольное приложение на Python, обеспечивающее:

- добавление пользователя в систему;
- авторизацию пользователя по идентификационным данным (логин + пароль);
- создание, редактирование, удаление и поиск конфиденциальных данных;
- те же операции над неконфиденциальными данными;
- деавторизацию пользователя.

Дополнительно реализовать осмысленные механизмы защиты:

- роли **admin / user / guest** с разграничением прав:
  - `guest` — только чтение неконфиденциальных данных;
  - `user` — CRUD неконфиденциальных данных + чтение **своих** конфиденциальных;
  - `admin` — полный доступ к данным и управлению пользователями;
- хранение паролей — PBKDF2-HMAC-SHA256 (стандартная библиотека `hashlib`);
- сессии с тайм-аутом;
- пометка данных как конфиденциальных и их шифрование AES-GCM
  (пакет `cryptography`), ключ выводится из мастер-пароля и на диске не хранится;
- журнал аудита действий;
- демонстрация всех операций с понятным логом, сохраняемым в `demo_output/`;
- отчёт с анализом защищённости приложения по четырём политикам:
  политика безопасности ОС, политика безопасности компонентов и их
  взаимодействия, сетевая политика, безопасность конфиденциальности данных.

## 2. Описание разработанного приложения

### 2.1. Архитектура

Приложение — консольное, без сетевых интерфейсов. Слоистая структура:

| Модуль | Назначение |
|---|---|
| `app/security.py` | криптопримитивы: PBKDF2-HMAC-SHA256 (200 000 итераций), AES-256-GCM (nonce 12 байт на каждую операцию) |
| `app/sessions.py` | менеджер сессий: токен `secrets.token_urlsafe(32)`, TTL 1800 с, проверка истечения при каждом обращении |
| `app/audit.py` | журнал аудита: построчный JSON (`ts, actor, action, target, result`), файл 0600 |
| `app/storage.py` | JSON-хранилище (`users.json`, `records.json`, `kdf.salt`): каталог 0700, файлы 0600, атомарная запись через временный файл и `os.replace` |
| `app/service.py` | бизнес-логика: аутентификация, роли, матрица прав, CRUD и поиск записей, шифрование конфиденциальных полей, записи в аудит |
| `app/demo.py` | демонстрационный сценарий всех операций (точка входа контейнера) |
| `app/cli.py` | интерактивная консоль |

Данные хранятся в `/srv/data` внутри контейнера; на хост ничего не
монтируется на запись. Конфиденциальная запись хранится как поле
`enc_payload` = base64(nonce ‖ AES-GCM(JSON{title, content})); у
неконфиденциальной записи `title`/`content` лежат в открытом виде — это
осознанное разграничение режимов хранения.

### 2.2. Идентификация, аутентификация, сессии

- Пароль пользователя: 16-байтовая случайная соль (`os.urandom`) +
  `hashlib.pbkdf2_hmac("sha256", pwd, salt, 200_000)`; в хранилище попадают
  только соль (base64) и хэш (hex). Сравнение — `hmac.compare_digest`
  (constant-time).
- Успешная аутентификация создаёт сессию со случайным 256-битным токеном
  и сроком жизни 1800 с. Каждый вызов операции проверяет токен и срок;
  истёкшая/неизвестная сессия — отказ `AccessDenied`.
- Деавторизация (`logout`) удаляет токен; удаление пользователя принудительно
  закрывает все его сессии.

### 2.3. Разграничение доступа

Матрица прав (реализована в `service.py`, проверяется до каждой операции,
каждый отказ фиксируется в аудите):

| Операция | guest | user | admin |
|---|---|---|---|
| чтение/поиск неконфиденциальных | да | да | да |
| чтение конфиденциальных | нет | только своих | всех |
| создание записей | нет | да (конфиденциальная → владелец = автор) | да |
| изменение/удаление записей | нет | своих | любых |
| добавление/удаление пользователей | нет | нет | да |

### 2.4. Аудит

Все значимые события (вход успешно/неуспешно, logout, управление
пользователями, CRUD и поиск записей, каждый отказ) пишутся в
`data/audit.log`. В журнал намеренно не попадают пароли, ключи и содержимое
записей — только субъект, действие, объект и результат.

### 2.5. Демонстрация

`./run.sh` собирает образ и запускает `demo.py` в контейнере; вывод
(108 строк) сохраняется в `demo_output/demo_run.log`. Сценарий показывает:
инициализацию, отказ при неверном пароле, успешный вход, создание
пользователей admin'ом, отказ на слабый пароль и недопустимую роль, CRUD
конфиденциальных и неконфиденциальных записей, поиск, запрет гостю на запись
и на чтение конфиденциальных, запрет user'у читать чужое конфиденциальное,
истечение тайм-аута сессии, отказ после logout, полный доступ admin'а,
состояние хранилища (видимый шифротекст `enc_payload`), хвост журнала аудита
и права файлов (все 0600).

## 3. Анализ защищённости приложения

### 3.1. Политика безопасности ОС (что приложение требует от ОС)

- **Права файлов.** Все файлы данных создаются с правами `0600` в каталоге
  `0700` (`umask 077` + явный `chmod`): чтение/запись только владельцу
  процесса, доступ группы и остальных исключён. Подтверждено демо:
  `audit.log: 0o600, kdf.salt: 0o600, records.json: 0o600, users.json: 0o600`.
  Запись атомарная (`tmp` + `os.replace`), исключая повреждение файлов при сбое.
- **Непривилегированный пользователь.** Контейнер выполняется от
  `appuser` (uid 10001), а не от root: компрометация приложения не даёт
  злоумышленнику прав суперпользователя.
- **Изоляция среды.** Базовый образ зафиксирован (`python:3.12-slim`),
  из состава зависимостей — только `cryptography` (закреплена версия 44.0.1).
  Композитный проект изолирован (`name: lab_1`), сеть не публикуется,
  volume'ов на запись на хост нет — приложение не может изменять файлы хоста.
- **Требования к ОС минимальны**: POSIX-права доступа к файлам, локальная ФС,
  никаких привилегий, setuid, устройств и сети.

### 3.2. Политика безопасности компонентов приложения и их взаимодействия

- **Разделение модулей**: криптопримитивы (`security`), хранилище
  (`storage`), сессии (`sessions`), аудит (`audit`) и бизнес-логика
  (`service`) разделены; доступ к данным возможен только через `service`,
  который перед каждой операцией проверяет сессию и права.
- **Единая точка контроля доступа**: проверки `_can_read`/`_can_write`/
  роли централизованы; отказ сопровождается записью в аудит и управляемым
  исключением (`AccessDenied`, `AuthError`, `ValidationError`, `NotFound`) —
  некорректный ввод (короткий пароль, пустой заголовок, неизвестный id,
  недопустимая роль) отклоняется без аварийного завершения.
- **Сессии как граница доверия**: субъект операции определяется только по
  действительному токену; тайм-аут ограничивает окно использования
  похищенного токена; logout и удаление пользователя инвалидируют токены.
- **Аудит как средство обнаружения**: фиксируются и успешные, и отклонённые
  действия (в демо-журнале видны и `allow`, и `deny`), что даёт материал
  для разбора инцидентов.
- Взаимодействие компонентов — прямые вызовы в одном процессе, внешних
  IPC/очередей нет; доверенная граница одна — ФС с правами 0600/0700.

### 3.3. Сетевая политика безопасности

- Приложение **не слушает сеть** (нет сокетов, серверных библиотек) и не
  инициирует сетевых соединений: поверхность сетевых атак отсутствует;
  compose-сервису не назначено ни одного порта.
- Если бы приложение стало сетевым (клиент-сервер), потребовались бы:
  обязательный TLS 1.2+ (лучше mutual TLS) для защиты канала; аутентификация
  сервера; ограничение попыток входа (anti-bruteforce, задержки, блокировка);
  привязка слушателя к необходимому интерфейсу; разграничение на уровне
  сети (доступ только из доверенного сегмента); защита сессий на стороне
  клиента; логирование IP-источников событий в аудит.

### 3.4. Безопасность конфиденциальности данных

- **Пароли**: PBKDF2-HMAC-SHA256, 200 000 итераций, уникальная 16-байтовая
  соль на пользователя — офлайн-подбор по `users.json` дорог, радужные
  таблицы бесполезны (соли разные), в файле нет ни одного пароля в открытом виде.
- **Конфиденциальные данные**: AES-256-GCM (аутентифицированное шифрование —
  конфиденциальность + целостность), случайный 12-байтовый nonce на каждую
  операцию (переиспользование nonce исключено), в `records.json` виден только
  шифротекст `enc_payload` (подтверждено демо). Поиск по конфиденциальным
  записям выполняется после расшифровки и только для допущенных ролей.
- **Ключ**: выводится PBKDF2 (200 000 итераций, соль `kdf.salt` 32 байта)
  из мастер-пароля, который берётся из переменной окружения; ни ключ, ни
  мастер-пароль на диске не хранятся. Компрометация `records.json` без
  мастер-пароля не раскрывает данные.
- **Разграничение**: конфиденциальные данные недоступны guest, чужие — user;
  доступ возможен только после аутентификации и в пределах живой сессии.
- **Аудит не раскрывает секретов**: в журнал не пишутся пароли, ключи и
  содержимое записей (только идентификаторы).

## 4. Анализ защищённости конфиденциальной информации

Модель угроз и состояние контрмер:

| Угроза | Контрмера | Состояние |
|---|---|---|
| Чтение файла данных посторонним на хосте | права 0600/0700 + шифрование AES-GCM конфиденциальных записей | реализовано, подтверждено демо |
| Офлайн-подбор паролей по users.json | PBKDF2 200k + уникальные соли | реализовано |
| Компрометация records.json (копия файла) | без мастер-пароля данные не расшифровываются (AES-256-GCM) | реализовано |
| Использование украденного токена | TTL 1800 с, logout, инвалидация при удалении пользователя | реализовано |
| Несанкционированный доступ по ролям | централизованная матрица прав + аудит отказов | реализовано |
| Подмена/повреждение записей | GCM-тег обнаружит повреждение шифротекста; атомарная запись | реализовано |
| Подделка журнала аудита | аудит вне матрицы прав, файл 0600; криптозащита целостности журнала отсутствует | остаточный риск |
| Компрометация памяти процесса (ключ в RAM) | вне границ лабораторной работы; типовой остаточный риск для прикладного ПО | остаточный риск |
| Слабый/утёкший мастер-пароль | проверка минимальной длины; ротация требует перешифрования | частично (нет политики ротации) |

Вывод по разделу: конфиденциальная информация защищена на уровне,
адекватном учебной задаче (шифрование при хранении, стойкое хэширование
паролей, разграничение доступа, аудит). Основные остаточные риски связаны не
с алгоритмами, а с операционными аспектами: хранением мастер-пароля (env),
отсутствием защиты целостности журнала и отсутствием механизма блокировки
при переборе паролей.

## 5. Вывод

**Семантическая составляющая.** Разработано консольное приложение управления
пользователями и данными с полным набором требуемых операций: добавление и
удаление пользователей, вход/выход, CRUD и поиск по конфиденциальным и
неконфиденциальным данным. Осмысленно реализованы механизмы безопасности:
роли admin/user/guest с централизованной матрицей прав; хранение паролей в
виде PBKDF2-HMAC-SHA256-хэшей с индивидуальными солями; сессии с тайм-аутом
и инвалидацией; шифрование конфиденциальных записей AES-256-GCM ключом,
выводимым из мастер-пароля; журнал аудита без секретов; права доступа к
файлам 0600/0700 и работа в контейнере от непривилегированного пользователя.
Демонстрационный прогон (108 строк лога в `demo_output/`) экспериментально
подтвердил каждый механизм: неверный пароль отклонён, гостю запрещены запись
и чтение конфиденциальных данных, user не видит чужих конфиденциальных
записей, истёкшая сессия и токен после logout недействительны, на диске
конфиденциальные записи представлены только шифротекстом.

**Прагматическая составляющая.** Получен переиспользуемый образец
безопасного проектирования прикладной системы: шаблон матрицы прав,
интеграции аудита, работы с секретами (мастер-пароль только через
окружение, ключ только в памяти) и защищённого хранения (права файлов +
аутентифицированное шифрование). Такой каркас применим как основа для
реальных задач хранения чувствительных данных (менеджеры учетных данных,
конфигурации с секретами, локальные хранилища персональных данных).
Проведённая оценка защищённости дала измеримые результаты (число итераций
KDF, права файлов, состав журнала, поведение при отказах), которые можно
проверять автоматически — что и сделано в лабораторной работе 2.
