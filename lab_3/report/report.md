# Лабораторная работа 3. Анализ безопасности кода

**Вариант:** приложение с интерактивным консольным UI, хранящее в оперативной
памяти данные двух классов (конфиденциальные / неконфиденциальные), с
анализом защищённости кода, замерами ОЗУ/CPU и анализом дампов памяти в трёх
точках жизненного цикла данных.

Все эксперименты выполнены внутри Docker-контейнера на базе `python:3.12-slim`
(Python 3.12.15, gdb + binutils, пакет `cryptography`). Выводы в отчёте —
только реально захваченный вывод программ из `demo_output/`.

---

## 1. Постановка задачи

1. Разработать приложение с интерактивным консольным UI, которое создаёт,
   обновляет и удаляет данные в оперативной памяти. Данные двух типов:
   **конфиденциальные** и **неконфиденциальные**. После ввода
   конфиденциальных данных выполняется их шифрование (AES-256-GCM из пакета
   `cryptography`; ключ выводится из мастер-пароля, в памяти хранится только
   шифртекст в `bytearray`) или хеширование (пароли — PBKDF2-HMAC-SHA256).
2. Провести анализ безопасности разработанного приложения с точки зрения
   кода: обработка невалидного ввода, lifetime секретов, затирание памяти,
   логирование, обработка исключений.
3. Проанализировать использование оперативной памяти и процессорного
   времени: замеры VmRSS (`/proc/self/status`) до/после операций и
   процессорного времени (`time.process_time()`), сводная таблица.
4. Снять дампы оперативной памяти (gdb gcore) в трёх точках — после ввода
   данных, после обновления, после удаления — в двух режимах: **safe**
   (шифрование + bytearray + затирание) и **unsafe** (plaintext `str` в
   памяти), выполнить поиск секретов в дампах и показать на реальных дампаx,
   что в unsafe секреты находятся, в safe — нет.
5. Оформить отчёт с выводом.

## 2. Краткое описание приложения

### 2.1. Состав и запуск

| Файл | Назначение |
|---|---|
| `app/vault.py` | ядро: `SafeVault` (шифрование/хэширование/затирание) и `UnsafeVault` (plaintext) |
| `app/main.py` | интерактивный консольный UI (`--mode safe\|unsafe`) |
| `app/bench.py` | замеры RSS/CPU → `demo_output/metrics.{md,csv}` |
| `app/run_demo.py` | драйвер демонстрации: сессии, bench, дампы, анализ |
| `run.sh` | одна команда: сборка + демонстрация в контейнере + сохранение вывода |

Запуск: `./run.sh` (Docker Compose, проект `lab_3`; контейнеру добавлены
`SYS_PTRACE` и `seccomp=unconfined` — этого требует снятие дампов через gdb).

### 2.2. Функциональность UI

Команды (одинаковы в обоих режимах): `add secret|public|password <id>`,
`get <id>`, `verify <id>`, `update <id>`, `delete <id>`, `list`, `stats`,
`dumpcore <путь>` (демо-команда снятия дампа), `help`, `quit`.

Классы данных:

- `secret` — конфиденциальные данные; сразу после ввода шифруются
  AES-256-GCM (nonce 12 Б, `os.urandom`), в памяти остаётся только
  шифртекст в `bytearray`;
- `password` — пароли; хранится только PBKDF2-HMAC-SHA256-хэш
  (600 000 итераций, персональная соль 16 Б) в `bytearray`; предусмотрена
  проверка `verify` через `hmac.compare_digest` (constant-time);
- `public` — неконфиденциальные данные; хранятся открыто (осознанное
  решение: затирание касается только конфиденциальных данных).

Ключ шифрования выводится из мастер-пароля при старте сессии:
PBKDF2-HMAC-SHA256, 600 000 итераций, соль `os.urandom(16)`. Мастер-пароль
введённой строки после вывода ключа удаляется из области видимости, куча
перезаписывается (`scrub_free_memory`).

### 2.3. Два режима (для пункта 4 задания)

- **safe** (`SafeVault`): описанная выше схема — шифртекст в `bytearray`,
  хэши паролей в `bytearray`, затирание буферов при обновлении/удалении,
  `scrub_free_memory()` (перезапись освобождённых блоков кучи) после каждой
  операции с секретами;
- **unsafe** (`UnsafeVault`): значения хранятся обычными `str`, мастер-пароль
  живёт в памяти всю сессию, «журнал операций» сохраняет ссылки на значения
  (в том числе «удалённых» записей — типовая ошибка реальных приложений),
  затирание отсутствует.

Валидация входных данных в обоих режимах **идентична** — различие режимов
сознательно сведено только к обращению с памятью, чтобы сравнение дампов
было корректным.

## 3. Анализ защищённости с точки зрения кода

### 3.1. Обработка невалидного ввода

Все пользовательские данные проходят валидацию до использования
(`app/vault.py`): тип записи — из белого списка `secret|public|password`;
идентификатор — непустой, ≤ 64 символов, без пробельных символов; значение —
непустое, ≤ 4096 символов; запрещены дубликаты идентификаторов. Ошибки
ввода оформлены отдельным классом `ValidationError` и **не** завершают
приложение: UI печатает `[err] …` и продолжает работу. Валидация выполняется
**до** запроса секретного значения, чтобы ошибочная команда не заставляла
пользователя вводить секрет (см. `cmd_add` в `app/main.py`).

Реальный вывод интерактивной сессии (`demo_output/session_safe.transcript.txt`;
24 команды, из них 14 `[ok]`, 10 `[err]` — все ошибки обработаны без падения):

```text
>>> add secret card1
>>> <значение скрыто (см. tokens.txt)>
vault[safe]> Значение: [ok] добавлена запись id=card1 type=secret
>>> add secret card1
>>> <значение скрыто (см. tokens.txt)>
vault[safe]> Значение: [err] запись 'card1' уже существует
>>> add bogus bad_id
vault[safe]> [err] неизвестный тип записи 'bogus'; допустимо: secret, public, password
>>> add secret
vault[safe]> [err] формат: add <secret|public|password> <id>
>>> get missing_id
vault[safe]> [err] запись 'missing_id' не найдена
>>> verify card1
vault[safe]> [err] запись 'card1' не является паролем
>>> bogus_command
vault[safe]> [err] неизвестная команда 'bogus_command' (help -- список команд)
```

Обрыв ввода (EOF) обрабатывается корректно и в основном цикле, и при вводе
значений (`read_line`, `ask_value`): приложение завершается с сообщением, а не
трассировкой.

### 3.2. Lifetime секретов в памяти

Принцип: секрет живёт в открытом виде минимально необходимое время.

- Введённое значение — `str` из `read_line()`; собственный bytearray-буфер
  чтения затирается сразу после декодирования (`app/main.py`, `read_line`).
  Специально **не используется `input()`**: его буфер читает поток с
  опережением и долго удерживает уже потреблённые байты — секрет оставался бы
  в живом внутреннем буфере `sys.stdin`, куда `scrub` не добирается (этот
  эффект реально наблюдался при отладке и воспроизведён в дампах; после
  перехода на `os.read`-чтение он исчез).
- Для `secret`: `value.encode()` → AES-GCM → `bytearray` шифртекта;
  открытый текст и промежуточные `bytes` освобождаются (`del`), локальные
  ссылки обнуляются (`del value` в `cmd_add`/`cmd_get`), затем выполняется
  `scrub_free_memory()`.
- Для `password`: открытый пароль существует только внутри `derive_key`
  (передаётся в PBKDF2 как `bytes`), хэш и соль — `bytearray`.
- Обновление: новые nonce+шифртекст записываются в запись только **после**
  затирания старых (`erase_bytearray`); удаление: затирание всех полей записи
  перед удалением словаря.
- Известные неустранимые ограничения (честно фиксируются): `str`/`bytes` в
  CPython неизменяемы — их нельзя затереть напрямую, только освободить и
  перезаписать кучу scrub-ом; AESGCM держит копию ключа в Rust-части
  `cryptography`, которую из Python не затереть; вытесненные на swap/в ядро
  страницы из-под контроля процесса не находятся (в контейнере demo swap не
  используется).

### 3.3. Затирание памяти

Два механизма (`app/vault.py`):

1. `erase_bytearray(buf)` — поэтичное заполнение нулями + `clear()` для всех
   изменяемых буферов перед удалением/заменой;
2. `scrub_free_memory()` — перезапись **уже освобождённых** блоков: выделяются
   обнулённые `bytearray` размеров от 16 до 65536 байт (покрывают классы
   pymalloc ≤512 Б и libc malloc до порога mmap), 2 прохода, с `gc.collect()`
   до и после. Стоимость — 2.06 мс на вызов (см. §4).

Расшифрованное значение при `get` показывается пользователю, после чего
ссылка удаляется и выполняется scrub.

### 3.4. Логирование

Значения секретов **никогда** не выводятся в лог/транскрипт: сообщения
`[ok]/[err]` содержат только идентификаторы и типы; сообщения об ошибках не
включают исключение целиком (только класс), чтобы секрет не «утёк» через
текст исключения. Исключение — явная команда `get`: расшифровка показывается
по требованию пользователя (это функциональность хранилища). В транскриптах
демо секретные значения ввода замаскированы драйвером (`<значение скрыто>`),
сами маркеры опубликованы отдельно в `dumps/tokens.txt` для воспроизводимости
поиска по дампам.

### 3.5. Исключения и отказоустойчивость

`ValidationError` — штатная ветка (сообщение пользователю, продолжение
работы). Любое другое исключение в команде перехватывается общим обработчиком
и печатается как `[err] внутренняя ошибка: <класс>` — UI не падает и не
печатает стек (в стеке могли бы быть значения). `dumpcore` изолирован
отдельным обработчиком. Аварийные ситуации, проверенные в сессии: неизвестная
команда, неверный формат, дубликат, обращение к несуществующей записи,
`verify` для не-пароля, EOF — всё обработано (10/10 ошибочных сценариев
завершились корректным `[err]`).

## 4. Анализ оперативной памяти и процессорного времени

Методика: `app/bench.py` выполняет одинаковые фазы в каждом режиме;
VmRSS читается из `/proc/self/status` до/после фазы, CPU —
`time.process_time()`, wall — `time.perf_counter()`. Объём: 400
конфиденциальных записей (значение 64 Б → 128 hex-символов) + 200
неконфиденциальных. Полные данные: `demo_output/metrics.md`, `metrics.csv`.

Сводная таблица (реальный прогон в контейнере):

| safe | add secret ×400 | 400 | 26744 | 26972 | 228 | 0.536 | 0.536 | 1.3401 |
| safe | add public ×200 | 200 | 26972 | 27056 | 84 | 0.2562 | 0.2562 | 1.2809 |
| safe | update secret ×400 | 400 | 27056 | 27056 | 0 | 0.5292 | 0.5292 | 1.323 |
| safe | get all ×600 | 600 | 27056 | 27188 | 132 | 0.0024 | 0.0024 | 0.004 |
| safe | delete secret ×400 | 400 | 27188 | 27188 | 0 | 0.5429 | 0.5433 | 1.3583 |
| safe | delete public ×200 | 200 | 27188 | 27188 | 0 | 0.27 | 0.27 | 1.3502 |
| unsafe | init | 1 | 27188 | 27188 | 0 | 0.0 | 0.0 | 0.0375 |
| unsafe | add secret ×400 | 400 | 27188 | 27188 | 0 | 0.0009 | 0.0009 | 0.0022 |
| unsafe | add public ×200 | 200 | 27188 | 27208 | 20 | 0.0004 | 0.0004 | 0.002 |

| unsafe | get all ×600 | 600 | 27332 | 27336 | 4 | 0.0003 | 0.0003 | 0.0005 |
| unsafe | delete secret ×400 | 400 | 27336 | 27356 | 20 | 0.0002 | 0.0002 | 0.0006 |
| unsafe | delete public ×200 | 200 | 27356 | 27356 | 0 | 0.0001 | 0.0001 | 0.0007 |
| micro | PBKDF2-HMAC-SHA256 ×1 (600000 итераций) | 1 | 27356 | 27356 | 0 | 0.0964 | 0.0964 | 96.39 |
| micro | AES-256-GCM encrypt(128 Б) ×1000 | 1000 | 27356 | 27356 | 0 | 0.0007 | 0.0007 | 0.0007 |
| micro | scrub_free_memory() ×1 | 1 | 27356 | 27356 | 0 | 0.0021 | 0.0021 | 2.0584 |

Интерпретация:

1. **CPU.** Safe-режим медленнее на ~3 порядка на операцию с записью
   (1.34 мс против 0.0022 мс), но абсолютная стоимость мала. Доминируют не
   AES (0.7 мкс на шифрование 128 Б!), а связка PBKDF2 + затирание: вывод
   ключа из мастер-пароля — 97 мс (разовая операция), один `scrub` — 2.1 мс,
   и он вызывается после каждой операции с секретами.
2. **ОЗУ.** Рост RSS за весь прогон — 1.9–2.3 МиБ на 600 записей, разница
   между режимами в пределах шума (шифртект длиннее открытого текста лишь на
   nonce+тег ≈ 28 Б). Существенного оверхеда по памяти safe-подход не даёт.
3. **ΔRSS после delete = 0** в обоих режимах: освобождённая память
   **не возвращается** ОС ни аллокатором CPython (pymalloc удерживает арены),
   ни glibc — это подтверждает, что «удалить ссылку» ≠ «очистить память», и
   именно поэтому нужны затирание и scrub (§3.3), а не `del`.

## 5. Анализ дампов оперативной памяти

### 5.1. Методика

Дампы снимает само приложение (команда `dumpcore`) вызовом
`gdb -p <pid> -batch -ex 'gcore <файл>'` (контейнер запущен с
`--cap-add=SYS_PTRACE --security-opt seccomp=unconfined`; журнал gdb —
`dumps/*.core.gdb.log`). Три точки в каждом режиме:

- **p1 «после ввода»** — добавлены `doc1` (secret, A), `pwd1` (password, B),
  `note1` (public, C), `doc2` (secret, D);
- **p2 «после обновления»** — `doc1` обновлён значением E;
- **p3 «после удаления»** — удалены `doc1`, `doc2`, `pwd1`.

Маркеры секретов генерируются случайно во время демо (не константы в коде!),
передаются приложению через stdin и «не забегают вперёд»: драйвер отправляет
значение только после подтверждения предыдущего шага, поэтому ещё не
введённые секреты не могут попасть в память до дампа. Поиск: `strings -a
<core>` + `grep -F <маркер>`; полные списки строк — `dumps/*.strings.txt`,
совпадения — `*.matches.txt`, окна памяти с найденными байтами —
`evidence_*.txt`. Маркеры прогона (см. `dumps/tokens.txt`):

```text
MASTER=MP-FB157E4DE453        SECRET_A=CARD-D15A3C67C069
PASSWORD_B=PWD-3E184B080974   PUBLIC_C=NOTE-PUBLIC-EB5A47D6
SECRET_D=CARD-AA7ADC2189D3    SECRET_E=CARD-C1DFA7D76A26
```

### 5.2. Результаты: сводная таблица поиска

Число найденных строк с маркером (реальный анализ, `dumps/dumps_analysis.md`):

| Маркер | safe·p1 ввод | safe·p2 обновл. | safe·p3 удаление | unsafe·p1 ввод | unsafe·p2 обновл. | unsafe·p3 удаление |
|---|---:|---:|---:|---:|---:|---:|
| MASTER (мастер-пароль) | **0** | **0** | **0** | 1 | 1 | 1 |
| SECRET_A (конфиденц.) | **0** | **0** | **0** | 1 | 1 | 1 |
| PASSWORD_B (пароль) | **0** | **0** | **0** | 1 | 1 | 1 |
| PUBLIC_C (неконфиденц.) | 1 | 1 | 1 | 1 | 1 | 1 |

| SECRET_E (новое знач.) | **0** | **0** | **0** | 0 | 1 | 1 |

### 5.3. Unsafe: секреты НАХОДЯТСЯ

Во всех трёх дампах unsafe-режима находятся мастер-пароль, оба
конфиденциальных значения и пароль — **включая точку p3 после их удаления**:
записи удалены из словаря, но `str`-объекты живы (ссылки из «журнала
операций») и/или остаются в не перезаписанных освобождённых блоках. Реальный
фрагмент дампа `unsafe_p3_delete.core` (смещение 0x376ec0, см.
`dumps/evidence_unsafe_p3_delete_SECRET_A.txt`) — удалённый секрет виден как
живой `str`-объект CPython (перед данными — служебное поле длины 0x11 = 17):

```text
00376ec0  43 41 52 44 2d 44 31 35 41 33 43 36 37 43 30 36  |CARD-D15A3C67C06|
00376ed0  39 00 42 d9 6f 78 00 00 00 00 00 00 00 00 00 00  |9.B.ox..........|
```

Вывод `grep` по точке p3 (`dumps/unsafe_p3_delete.core.matches.txt`):


### 5.4. Safe: секреты НЕ НАХОДЯТСЯ

Во всех трёх safe-дампах не найден **ни один** секретный маркер: ни
мастер-пароль, ни конфиденциальные данные (введённые, старые после
обновления, «удалённые»), ни пароль. Единственная находка во всех safe-дампах
— PUBLIC_C, неконфиденциальная запись, которая по дизайну хранится открыто
(см. `dumps/evidence_safe_p3_delete_PUBLIC_C.txt`). Вывод `grep` по точке
p3 (`dumps/safe_p3_delete.core.matches.txt`):

```text
## PUBLIC_C (найдено строк: 1)
NOTE-PUBLIC-EB5A47D6

## MASTER (найдено строк: 0)
## SECRET_A (найдено строк: 0)
## PASSWORD_B (найдено строк: 0)
## SECRET_D (найдено строк: 0)
## SECRET_E (найдено строк: 0)
```

При этом в safe-дампе p1 шифртексты записей присутствуют (хранятся в памяти
осознанно), но поиск по открытым маркерам их не находит — AES-GCM делает
шифртекст вычислительно неотличимым от случайных данных, а открытый текст
существует внутри цикла шифрования и вычищается scrub-ом.

### 5.5. Ограничения анализа

- Дампы хранятся усечённо при >48 МиБ (в этом прогоне каждый дамп ~16.5 МиБ
  и сохранён полностью); анализ `strings`/`grep` выполняется по полному дампу
  до усечения, его полный вывод сохранён в `*.strings.txt`/`*.matches.txt`.
- Отсутствие маркера в дампе — сильный, но не абсолютный признак отсутствия
  секрета: байты могли быть вытеснены в swap/ядро или попасть в области,
  не попавшие в core-файл. Для demo-среды (контейнер без swap) это
  приемлемое ограничение.
- Python-специфика (неизменяемость `str`, копия ключа в Rust-библиотеке)
  означает, что safe-подход даёт *инженерный* (best-effort), а не
  формально доказуемый уровень защиты остаточных данных; при этом
  практически значимый результат достигнут и подтверждён дампами.

## 6. Вывод

**Семантическая составляющая.** В ходе работы реализовано и исследовано
хранилище с двумя классами данных и показано, что защищённость приложения
«в памяти» определяется не одним механизмом, а их связкой: криптография
(AES-256-GCM для данных, PBKDF2 для паролей) устраняет *персистентное*
присутствие секрета в ОЗУ; дисциплина lifetime (минимум времени жизни,
немедленное освобождение ссылок) сокращает окно раскрытия; затирание
`bytearray` + перезапись освобождённых блоков кучи устраняет *остаточные*
данные; отказ от буферизованного ввода (`input()` → `os.read`) устраняет
скрытые копии в служебных буферах. Эксперимент с дампами это подтверждает
количественно: в unsafe-режиме 5 из 5 секретных маркеров находятся во всех
точках, включая точку после удаления (5 находок в p3); в safe-режиме — 0
секретных маркеров во всех точках, при этом неконфиденциальные данные
находятся штатно (что подтверждает чувствительность метода поиска). Замеры
показали, что цена безопасного подхода в данной задаче пренебрежима по
памяти (~единый масштаб RSS) и умеренна по CPU (≈1.3 мс на операцию
против ≈0.002 мс; доминирует затирание и PBKDF2, но не AES). Одновременно
зафиксированы принципиальные границы: неизменяемость `str` и внешние
(Rust/ядро) копии не позволяют в управляемой среде гарантировать полное
исчезновение секрета — возможен лишь инженерно обоснованный минимум.

**Прагматическая составляющая.** Полученные результаты непосредственно
переносимы
на практику: (1) приём «снять дамп и grep-нуть маркеры» — дешёвый и
воспроизводимый способ аудита реальных приложений (менеджеры паролей, токены
сессий, ключи API) и должен входить в регламенты проверки кода, работающего
с секретами; (2) типовые находки unsafe-режима — хранение секретов в
str/логах/«журналах операций», ключи без затирания — это те дефекты, которые
реально встречаются и находятся статическим анализом + дампами; (3)
практические рекомендации для разработчика: шифровать секрет сразу после
ввода и хранить только шифртекст в изменяемых буферах; затирать буферы при
обновлении/удалении; периодически перезаписывать освобождённую кучу;
не логировать секреты и не включать их в сообщения об ошибках; валидировать
ввод до запроса секрета; учитывать, что `del` в Python не очищает память;
отключать swap/рассматривать `mlock` для критичных сервисов. Для систем с
жёсткими требованиями (сертифицируемые СЗИ) нужно выходить за пределы
управляемой среды (native-код с `memset_s`/`explicit_bzero`, `mlock`,
контроль страниц памяти), поскольку средствами самого Python остаточные
данные устраняются не гарантированно, а best-effort.
