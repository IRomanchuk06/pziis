# Лабораторная работа 2. Оценка защищённости сторонней программной системы

## 1. Постановка задачи

1. Разработать **методику оценки защищённости** программных систем:
   формальный список проверок по четырём политикам — политика безопасности
   ОС, политика безопасности компонентов и их взаимодействия, сетевая
   политика, безопасность конфиденциальности данных; каждая проверка —
   измеримый критерий с ожидаемым результатом и способом проверки.
2. Выполнить анализ предоставленного приложения (приложение лабораторной
   работы 1 — консольный менеджер пользователей и данных) по методике.
3. Реализовать скрипт-аудитор `app/audit.py`, который автоматически
   проверяет пункты методики: получает исходники lab_1 (volume-маунт
   только на чтение) и выполняет статические и динамические проверки
   (PBKDF2, отсутствие открытых паролей, тайм-аут сессий, отсутствие
   секретов в аудите, обработка невалидного ввода, отсутствие сетевых
   слушателей, права на файлы данных и др.). Вывод — таблица
   «проверка / ожидание / факт / вердикт» в `demo_output/`.
4. Предложить комплекс мер по усовершенствованию системы и рекомендации
   по её безопасному использованию.

## 2. Краткое описание предоставленной системы

Оцениваемая система — консольное приложение на Python 3.12 (см. `lab_1`):

- пользователи с ролями `admin/user/guest`; аутентификация по логину и
  паролю; пароли хранятся как PBKDF2-HMAC-SHA256 (200 000 итераций) с
  индивидуальными солями;
- сессии с токеном `secrets.token_urlsafe(32)` и тайм-аутом 1800 с;
- данные — записи двух классов: неконфиденциальные (открытый текст в
  `records.json`) и конфиденциальные (заголовок и содержимое зашифрованы
  AES-256-GCM, поле `enc_payload`); ключ AES-256 выводится PBKDF2 из
  мастер-пароля (окружение) с солью `kdf.salt`; на диске не хранится;
- разграничение: guest — чтение только неконфиденциальных; user — CRUD
  своих записей и чтение своих конфиденциальных; admin — всё;
- журнал аудита (JSON-строки, `allow/deny`) без паролей и содержимого;
- данные — в `/srv/data` (каталог 0700, файлы 0600), внутри контейнера
  от непривилегированного пользователя, без сети и без записи на хост.

## 3. Разработанная методика оценки защищённости

### 3.1. Принципы

- Каждая проверка — **измеримый критерий**: бинарный результат
  (соответствует / не соответствует) с наблюдаемым фактом.
- Для каждого критерия заданы: **ожидаемый результат** и **способ
  проверки** — статический (анализ исходников/Dockerfile), динамический
  (тестовый прогон системы в изолированной среде с известными
  аудиторскими секретами и маркерами) либо их комбинация.
- Проверяемые свойства должны быть **воспроизводимыми**: динамические
  тесты не зависят от состояния реального хранилища — среда создаётся
  заново на каждый прогон (`/srv/work`), известные аудиторские пароли и
  маркеры позволяют доказательно искать их утечки (в хранилище, в аудите,
  в коде).
- Вердикты: `PASS` / `FAIL` / `SKIP` (среда не поднята — честная
  неопределённость вместо ложного успеха).

### 3.2. Список проверок

Политика безопасности ОС:

| ID | Критерий (измеримый) | Ожидаемый результат | Способ |
|---|---|---|---|
| OS-S1 | Базовый образ зафиксирован (не `latest`), контейнер не от root (`USER` не-root) | `FROM python:3.12-slim`, `USER appuser` | статический (Dockerfile) |
| OS-D1 | Приложение работоспособно от непривилегированного uid | полный тестовый прогон при `euid != 0` | динамический |
| OS-D2 | Файлы данных недоступны group/others | каталог `0700`, все файлы `0600` (`mode & 0o077 == 0`) | динамический (`os.stat`) |

Политика безопасности компонентов и их взаимодействия:

| ID | Критерий | Ожидаемый результат | Способ |
|---|---|---|---|
| CMP-S1 | Пароли хэшируются PBKDF2-HMAC-SHA256 | вызов `pbkdf2_hmac('sha256', …)` в коде | статический |
| CMP-S2 | Стойкость KDF | число итераций ≥ 100 000 | статический |
| CMP-S3 | Соль пароля криптослучайна | `os.urandom` для соли | статический |
| CMP-S4 | Сессии имеют тайм-аут | константа `0 < TTL ≤ 8 ч`, проверка истечения при каждом доступе | статический |
| CMP-S5 | В ядре нет паролей-литералов | пароли — только параметры функций/env | статический |
| CMP-D1 | Неверный пароль отклоняется | `AuthError`, сессия не создаётся | динамический |
| CMP-D2 | Хранилище пользователей без открытых паролей | только соль + hex-хэш (64 символа), пароли аудитора не найдены | динамический (файл) |
| CMP-D3 | Соли уникальны у пользователей | число различных солей = числу пользователей | динамический |
| CMP-D4 | Тайм-аут применяется на практике | сессия с `ttl=1 c` недействительна через 1.4 c | динамический |
| CMP-D5 | Logout инвалидирует токен | операция по токену после logout → `AccessDenied` | динамический |
| CMP-D6 | Аудит фиксирует успехи и отказы | в журнале есть записи `allow` и `deny` | динамический (файл) |
| CMP-D7 | Аудит не содержит секретов | пароли и маркер секрета не встречаются в `audit.log` | динамический (файл) |
| CMP-D8 | Некорректный ввод отклоняется управляемо | 5 видов невалидного ввода → `ValidationError/NotFound`, без аварий | динамический |

Сетевая политика безопасности:

| ID | Критерий | Ожидаемый результат | Способ |
|---|---|---|---|
| NET-S1 | В коде нет сетевых API | отсутствуют `socket`, `socketserver`, `http.server`, `flask`, `fastapi`, `uvicorn`, `aiohttp`, `urllib`, `requests` | статический |
| NET-D1 | Нет слушателей приложения | в `/proc/net/tcp*` нет `LISTEN`, кроме атрибутированной DNS-инфраструктуры Docker (127.0.0.11) | динамический (`/proc`) |

Безопасность конфиденциальности данных:

| ID | Критерий | Ожидаемый результат | Способ |
|---|---|---|---|
| CF-S1 | Конфиденциальные данные шифруются AES-GCM | `AESGCM`, случайный nonce 12 байт на операцию | статический |
| CF-S2 | Секреты не зашиты в исходники | аудиторские пароли отсутствуют в коде | статический |
| CF-D1 | Матрица прав guest/user/admin соблюдается | 6 тестов: гостю запрет записи/чтения чужого конф., user'у запрет чужого конф. и разрешение своего, admin'у разрешено всё | динамический |
| CF-D2 | Конфиденциальные записи зашифрованы на диске | в `records.json` только `enc_payload` (шифротекст), маркер секрета отсутствует | динамический (файл) |
| CF-D3 | Неконфиденциальные записи хранятся читаемо | маркер открытого текста присутствует (режимы различаются) | динамический (файл) |
| CF-D4 | Ключ и мастер-пароль не на диске | байты ключа и пароля отсутствуют во всех файлах данных | динамический (файлы) |

Итого: **24 проверки** (9 статических, 15 динамических).

### 4.2. Разбор результатов

- **ОС.** Система не требует привилегий и корректно работает от
  непривилегированного пользователя; хранилище недоступно другим
  пользователям хоста даже при наличии доступа к файловой системе контейнера.
- **Компоненты.** Криптопараметры паролей соответствуют современным
  рекомендациям (PBKDF2-HMAC-SHA256, 200 000 итераций, уникальные соли,
  constant-time сравнение). Граница доверия — сессия: и тайм-аут, и
  logout подтверждены динамически. Аудит достаточно полон (фиксирует
  отказы) и не создаёт вторичного канала утечки секретов.
- **Сеть.** Статический и динамический анализ согласуются: сетевых API нет,
  слушателей нет. Отмечен методически важный нюанс: в `/proc/net/tcp`
  контейнера присутствует слушатель `127.0.0.11` — встроенный DNS-прокси
  Docker, т.е. инфраструктура окружения; проверка была уточнена, чтобы
  атрибутировать таких слушателей и оценивать только сокеты, создаваемые
  самой системой. Первые прогоны аудитора также выявили дефекты в нём самом
  (разбор литерала `200_000`, права на рабочий каталог), что подтверждает
  полезность калибровки аудитора на заведомо известной цели.
- **Конфиденциальность.** На диске конфиденциальные записи представлены
  только шифротекстом AES-GCM; ключ и мастер-пароль в файлах данных
  отсутствуют; матрица прав подтверждена шестью негативными и позитивными
  тестами.

### 4.3. Ограничения оценки

- Аудит проверяет реализацию, а не формальную верификацию: отсутствие
  уязвимостей не доказывается.
- Криптостойкость мастер-пароля не оценивается (это свойство эксплуатации,
  а не кода).
- Тесты выполняются в окружении, аналогичном целевому (контейнер);
  поведение на иной ОС/ФС не проверялось.
- Не покрыто: восстановление после сбоя на середине записи, конкурентный
  доступ нескольких процессов, объёмные данные.

## 5. Комплекс мер по усовершенствованию

Краткосрочные (низкие затраты, высокий эффект):

1. **Мастер-пароль — из менеджера секретов** (docker secrets / vault), а не
   из `environment` compose-файла; исключить его появление в файлах
   проекта и в `docker inspect`.
2. **Ограничение попыток входа**: блокировка/задержка после N неудачных
   аутентификаций (данные — в аудите уже есть, нужен счётчик и политика).
3. **Целостность журнала аудита**: хэш-цепочка (каждая запись включает хэш
   предыдущей) или внешняя отправка в централизованный журнал (syslog),
   ротация и контроль доступа к `audit.log`.
4. **Ужесточение контейнера**: `read_only: true` для rootfs, `cap_drop: ALL`,
   `no-new-privileges`, запуск сети `none` (приложению сеть не нужна).
5. **Пин образа по digest** (`python:3.12-slim@sha256:…`) и сканирование
   образов на уязвимости (trivy/grype) в CI.

Среднесрочные:

6. **Переход на Argon2id** для паролей (защита от GPU-перебора) или рост
   параметров PBKDF2 с миграцией при входе пользователя (rehash-on-login).
7. **Ротация ключей шифрования**: версионирование ключа (`key_ver` в записи),
   процедура перешифрования при смене мастер-пароля.
8. **Резервное копирование и восстановление**: регламент бэкапа
   `/srv/data` с проверкой восстановления (включая расшифровку тестовой
   записи), хранение бэкапов отдельно от ключа.
9. **Автотесты безопасности в CI**: матрица прав и негативные сценарии
   (уже реализованные в аудиторе) как обязательный шаг pipeline.

Долгосрочные:

10. При появлении сетевого интерфейса — TLS 1.2+/mTLS, rate limiting,
    привязка к доверенному сегменту сети (см. сетевую политику в lab_1).
11. Двухфакторная аутентификация для роли admin; политика паролей
    (длина, история, срок действия).
12. Минимизация времени жизни секретов в памяти, рассмотреть хранение
    ключа во внешнем криптопровайдере (KMS) вместо вывода из мастер-пароля.

## 6. Рекомендации по безопасному использованию

- Запускать только в доверенном окружении; хост, на котором выполняется
  контейнер, должен быть сам защищён (права на проект, доступ по SSH,
  обновления), поскольку изоляция приложения — файловая, а не физическая.
- Мастер-пароль и пароль администратора передавать через секреты
  (`docker secret`, `--env-file` вне репозитория), не хранить в коде и
  compose-файлах; длина мастер-пароля — не менее 16 символов, генерация
  из криптослучайного источника.
- Регулярно просматривать `audit.log` (особенно записи `deny` и `login`);
  при аномалиях — менять мастер-пароль (с процедурой перешифрования) и
  пароли пользователей.
- Делать резервные копии каталога данных; хранить их с теми же правами
  (0600/0700) и отдельно от мастер-пароля; периодически проверять
  восстановление.
- Запускать с сетевой изоляцией (`docker run --network none` /
  `network_mode: none`), т.к. приложению сеть не требуется.
- Ограничивать TTL сессий на недоверенных машинах (переменная
  конфигурации TTL, например 5–10 минут) и завершать сессию (logout) по
  окончании работы.
- Не выносить каталог `/srv/data` на общедоступные ресурсы (общие папки,
  облачные синхронизации) без дополнительного шифрования уровня хранилища.
- При обновлении зависимостей/базы образа — повторять прогон аудитора
  `lab_2` как регрессионный тест защищённости.

## 7. Вывод

**Семантическая составляющая.** Разработана формальная методика оценки
защищённости по четырём политикам (ОС; компоненты и взаимодействие; сеть;
конфиденциальность данных) — 24 измеримых критерия с ожидаемыми
результатами и способами проверки, — и скрипт-аудитор, выполняющий их
автоматически: статический анализ исходников и Dockerfile цели плюс
динамический тестовый прогон системы в изолированной среде с известными
секретами и маркерами. По методике проанализировано приложение lab_1:
все 24 проверки завершены вердиктом PASS, в том числе негативные тесты
матрицы прав, подтверждение тайм-аута сессии, отсутствия паролей в
хранилище и в аудите, шифротекста конфиденциальных записей на диске и
отсутствия ключа в файлах. Побочный результат методологической ценности:
первые прогоны аудитора показали, как легко получить ложный
FAIL/ложный PASS (литерал `200_000`, право доступа к рабочему каталогу
аудитора, DNS-слушатель Docker в network namespace) — критерии должны
атрибутировать наблюдаемые факты, а не просто считать вхождения.

**Прагматическая составляющая.** Получен воспроизводимый инструмент
регрессионного контроля защищённости: после любого изменения кода или
зависимостей одна команда (`./run.sh`) за десятки секунд даёт
объективную таблицу «проверка / ожидание / факт / вердикт» и код
возврата для CI. Методика универсальна по форме (критерии + ожидания +
способ проверки) и переносима на другие системы — достаточно заменить
реализации проверок. Комплекс из 12 мер и рекомендации по эксплуатации
переводят систему из «безопасной по построению» в «безопасную по
эксплуатации»: устраняются главные операционные риски (хранение
мастер-пароля, отсутствие блокировки перебора, незащищённая целостность
аудита, отсутствие бэкапов и ротации ключей). Для владельца системы это
означает измеримый и проверяемый уровень гарантий вместо декларативного.
