# Лабораторная работа №11. Анализ запросов из сети Интернет (БГУИР)

Стенд полностью разворачивается в Docker: «удалённый сервер» — два контейнера
(веб-сервер nginx и SSH-сервер OpenSSH), генерация трафика и анализ выполняются
третьим контейнером-клиентом. На хосте ничего не устанавливается и не
запускается; порты наружу не публикуются — весь трафик ходит внутри сети
compose `lab_11_labnet`.

## Быстрый старт

```bash
./run.sh
```

Одна команда выполняет весь цикл:

1. сборку образов и запуск сервисов `web` (nginx) и `sshd` (OpenSSH);
2. синтетический **backfill** журналов за 5 предыдущих дней;
3. **живой прогон** — реальные `curl`-запросы (обычный просмотр + сканирование
   типичных уязвимых путей) и реальные SSH-попытки через `sshpass`
   (успешные входы + серия неверных паролей);
4. анализ журналов за все 6 дней;
5. сохранение журналов и результатов в `demo_output/`, остановку стенда.

Результаты:

| Файл | Содержимое |
|---|---|
| `demo_output/access.log` | журнал доступа nginx (кастомный формат с `X-Forwarded-For`) за 6 дней |
| `demo_output/error.log` | журнал ошибок nginx (уровень `warn`) |
| `demo_output/auth.log` | журнал SSH-сервера (сообщения `sshd`, syslog-подобный формат) |
| `demo_output/live_run.txt` | транскрипт живого прогона (команды curl/ssh и их результаты) |
| `demo_output/analysis_report.txt` | отчёт анализатора: статистика, детект брутфорса, вердикты |
| `report/report.md` | отчёт по лабораторной работе |

## Состав стенда

```text
docker-compose.yml        проект lab_11: сервисы web, sshd, client; сеть labnet
web/default.conf          конфиг nginx: log_format с X-Forwarded-For,
                          server_tokens off, /admin -> 403, /old -> 301
web/html/                 тестовая страница (index.html, about.html, style.css)
sshd/                     образ ubuntu:24.04 + openssh-server, sshd_config,
                          entrypoint (генерация host-ключей, журнал в auth.log)
client/                   образ python:3.12-slim + openssh-client, sshpass,
                          curl, requests, paramiko
generator/backfill.py     СИНТЕТИЧЕСКИЕ журналы за 5 предыдущих дней
generator/live.py         РЕАЛЬНЫЕ запросы текущего дня (curl + sshpass)
analysis/analyze.py       анализатор журналов (только stdlib Python)
runtime/logs/             журналы, куда пишут nginx и sshd (bind mount)
demo_output/              сохранённый реально захваченный вывод прогона
report/report.md          отчёт по лабораторной работе
```

## Учётная запись SSH

* пользователь: `labuser`
* пароль: `Lab11_Secret_Pass!` (лабовый, задан в `sshd/Dockerfile`)

Вход суперпользователя по SSH запрещён (`PermitRootLogin no`).

## Честность данных (важно)

Реальное время лабораторной работы растянуть нельзя, поэтому журналы за
6 дней формируются так:

* **Дни 1–5 (backfill) — синтетические**: их создаёт `generator/backfill.py` с
  фиксированным seed (воспроизводимо). Моделируются реалистичные
  распределения: часы пик (утро/вечер), доли кодов ответов, фоновые сканеры,
  две кампании брутфорса SSH (в т.ч. с «успешным» подбором пароля), фальшивый
  поисковый бот. Формат строк полностью соответствует реальным форматам nginx
  и sshd.
* **День 6 — реальные события**: их пишут сами серверы. `generator/live.py`
  выполняет настоящие `curl`-запросы (обычные и скан-пути `/etc/passwd`,
  `/.env`, `/wp-admin/`, ...) и настоящие SSH-попытки (`sshpass`: успешные
  входы и перебор неверных паролей). Записи попадают в те же файлы журналов.

Допущения, явно указываемые в отчёте:

* IP-адреса синтетической части взяты из документационных диапазонов
  RFC 5737 (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) и не указывают
  на реальные узлы;
* в реальной части веб-запросов «внешний» IP посетителя передаётся заголовком
  `X-Forwarded-For` (nginx пишет его в журнал), а фактический источник — IP
  контейнера `client` в сети compose; именно с этого внутреннего IP идут и
  реальные SSH-попытки;
* все отметки времени — в UTC.

## Как это работает изнутри

* nginx пишет `access.log` в кастомном формате `lab11`
  (`remote_addr`, запрос, статус, размер, referer, User-Agent,
  `xff="X-Forwarded-For"`) и `error.log` уровня `warn`; версия сервера скрыта
  (`server_tokens off`).
* sshd запускается с журналом в `/var/log/auth.log`; OpenSSH 9.6 при `-E`
  не пишет отметки времени, поэтому вывод sshd направляется через `ts`
  (пакет `moreutils`), добавляющий syslog-подобный префикс
  `YYYY-MM-DDThh:mm:ss+00:00 lab11-sshd sshd:`.
* Оба сервиса пишут журналы в один каталог хоста `runtime/logs/`
  (bind mount), анализатор читает их оттуда.

## Повторный запуск и очистка

```bash
./run.sh                 # чистый прогон заново (старые журналы удаляются)
docker compose down      # остановить стенд
docker compose down -v --rmi local   # убрать также собранные образы
```

При каждом запуске backfill детерминирован (seed фиксирован), реальные записи
живого прогона добавляются в конец журналов с текущими метками времени.
