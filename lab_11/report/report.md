## 1. Постановка задачи

Согласно заданию необходимо:

1. установить на «удалённом сервере» веб-сервер и разместить на нём тестовую
   страницу, доступную из сети;
2. настроить систему журналирования веб-сервера и SSH-сервера;
3. выполнить анализ журналов различных подсистем (веб-сервер, SSH) за
   несколько дней;
4. выявить подозрительную активность (сканирование, подбор паролей) и
   сформулировать рекомендации по повышению безопасности сервера;
5. оформить отчёт о проделанной работе.

«Удалённый сервер» воспроизведён локально с помощью Docker: это изолированный
стенд из трёх контейнеров в общей сети compose (`lab_11_labnet`), порты наружу
не публикуются:

* `web` — веб-сервер nginx (образ `nginx:1.27-alpine`) с тестовой страницей;
* `sshd` — SSH-сервер (Ubuntu 24.04 + OpenSSH 9.6p1) с парольным
  пользователем `labuser`;
* `client` — контейнер-клиент (python:3.12-slim + `openssh-client`,
  `sshpass`, `curl`, `requests`, `paramiko`), который генерирует трафик
  и запускает анализатор.

Такая реализация полностью покрывает задание и даёт воспроизводимость:
весь цикл (подъём стенда, генерация трафика, анализ, сохранение результатов)
выполняется одной командой `./run.sh`.

Журналы должны содержать данные **за несколько дней**. Растягивать реальное
время выполнения лабораторной нельзя, поэтому использован честный двухчастный
подход (явно помечен в README и во всех артефактах):

* **дни 1–5 — синтетический backfill**: скрипт `generator/backfill.py`
  (фиксированный seed — воспроизводимо) создаёт записи в форматах,
  идентичных реальным, с реалистичными распределениями: часы пик, доли кодов
  ответов, фоновые сканеры, две кампании брутфорса SSH, поддельный поисковый
  бот;
* **день 6 — реальные события**: скрипт `generator/live.py` выполняет
  настоящие `curl`-запросы (обычный просмотр + сканирование путей
  `/etc/passwd`, `/.env`, `/wp-admin/`, …) и настоящие SSH-попытки через
  `sshpass` (успешные входы и перебор неверных паролей); записи пишут **сами
  серверы** nginx и sshd в те же файлы журналов.

Допущения (указаны и в README): IP-адреса синтетической части взяты из
документационных диапазонов RFC 5737 (`192.0.2.0/24`, `198.51.100.0/24`,
`203.0.113.0/24`) и не указывают на реальные узлы; в реальной части
веб-запросов «внешний» IP передаётся заголовком `X-Forwarded-For` (фактический
источник — IP контейнера `client`, в данном прогоне `172.26.0.4`);
отметки времени — UTC.

## 2. Краткое описание веб-сервера

Веб-сервер — **nginx 1.27** в контейнере `lab11-web`. Размещена тестовая
страница (`index.html` — главная, `about.html` — «О сервере»,
`assets/style.css`), доступная по `http://web/` из сети стенда
(демонстрация: `demo_output/live_run.txt`, раздел 1 — `curl` возвращает HTML
страницы и HTTP 200).

Ключевые настройки (`web/default.conf`):

* кастомный формат журнала `lab11` с полем `X-Forwarded-For`:

  ```nginx
  log_format lab11 '$remote_addr - $remote_user [$time_local] '
                   '"$request" $status $body_bytes_sent '
                   '"$http_referer" "$http_user_agent" '
                   'xff="$http_x_forwarded_for"';
  access_log /var/log/nginx/access.log lab11;
  error_log  /var/log/nginx/error.log warn;
  ```

* `server_tokens off` — версия nginx не раскрывается в заголовке `Server` и на
  страницах ошибок;
* `location ^~ /admin { return 403; }` — «административный» раздел закрыт
  (попытки доступа журналируются со статусом 403);
* `location = /old { return 301 /about.html; }` — постоянный редирект
  (даёт статус 301 в журнале).

SSH-сервер — OpenSSH 9.6p1 (контейнер `lab11-sshd`): создан пользователь
`labuser` с паролем, `PermitRootLogin no`, `PasswordAuthentication yes`,
`LogLevel VERBOSE`. OpenSSH 9.6 при запуске с `-E <файл>` пишет строки **без**
отметок времени, поэтому вывод sshd направляется через утилиту `ts` (пакет
`moreutils`), добавляющую syslog-подобный префикс с меткой UTC; итоговый
`/var/log/auth.log` имеет канонический вид. Host-ключи генерируются при первом
старте контейнера (`ssh-keygen -A`).

Оба сервера пишут журналы в общий каталог стенда (`runtime/logs/`), откуда их
читает анализатор.

## 3. Краткое описание анализируемых файлов

### 3.1. access.log — журнал доступа веб-сервера

Назначение: фиксация **каждого HTTP-запроса** — кто, когда, что запрашивал и
какой получил ответ. Это основной источник для анализа трафика: топ клиентов,
популярность страниц, коды ответов, распределение нагрузки по часам, выявление
сканирования и автоматизированных клиентов.

Формат (кастомный `lab11`) и примеры строк:

```text
192.0.2.10 - - [01/Oct/2026:10:24:31 +0000] "GET / HTTP/1.1" 200 1174 "-" "Mozilla/5.0 ..." xff="192.0.2.10"
172.26.0.4 - - [05/Oct/2026:12:14:55 +0000] "GET /etc/passwd HTTP/1.1" 404 146 "-" "curl/8.5.0" xff="203.0.113.66"
```

| Поле | Смысл |
|---|---|
| первое поле | `$remote_addr` — фактический адрес соединения |
| `$time_local` | время запроса (UTC) |
| `"$request"` | метод, путь, версия протокола |
| `$status` | код ответа HTTP |
| `$body_bytes_sent` | размер отданного тела ответа |
| `"$http_referer"` | источник перехода |
| `"$http_user_agent"` | User-Agent клиента |
| `xff="…"` | `X-Forwarded-For` — «внешний» адрес клиента за прокси/имитация в стенде |

При анализе в качестве адреса клиента используется `xff`, а при его
отсутствии — `remote_addr`.

### 3.2. error.log — журнал ошибок веб-сервера

Назначение: диагностика работы самого сервера и **причин** ответов об ошибках.
Уровень `warn`. Пример строки (отсутствующий файл, запрошенный сканером):

```text
2026/10/03 13:07:12 [error] 30#30: *41817 open() "/usr/share/nginx/html/etc/passwd" failed (2: No such file or directory), client: 198.51.100.231, server: _, request: "GET /etc/passwd HTTP/1.1", host: "web"
```

Здесь: дата/время, уровень (`error`/`warn`/`notice`), идентификаторы рабочего
процесса и соединения, текст ошибки, клиент, сервер, исходный запрос.
Журнал позволяет отличить «битые ссылки» (регулярные 404 на свои ресурсы) от
сканирования (404 на типовые уязвимые пути), а также увидеть служебные
события (запуск/остановка рабочих процессов).

### 3.3. auth.log — журнал попыток входа в систему (SSH)

Назначение: фиксация **всех событий аутентификации** SSH-сервера: попытки
входа, имена пользователей, адреса источников, результат. Это главный источник
для выявления подбора паролей (аналог `/var/log/secure*` в CentOS, упомянутого
в теоретической части). Формат — syslog-подобный:

```text
2026-10-04T20:40:03.895941+00:00 lab11-sshd sshd[9984]: Failed password for labuser from 198.51.100.23 port 34710 ssh2
2026-10-05T12:14:55+00:00 lab11-sshd sshd:  Accepted password for labuser from 172.26.0.4 port 32876 ssh2
2026-10-05T12:15:00+00:00 lab11-sshd sshd:  kex_exchange_identification: client sent invalid protocol identifier "GET / HTTP/1.1"
```

Типовые сообщения, используемые при анализе: `Accepted password/publickey for
<user> from <ip>` — успешный вход; `Failed password for [invalid user] <user>
from <ip>` — неверный пароль; `Invalid user <user> from <ip>` — попытка входа
под несуществующим именем; `Connection closed by … [preauth]` — разрыв до
завершения аутентификации; `kex_exchange_identification: …` — обращение к
порту 22 не по протоколу SSH (сканирование).

## 5. Рекомендации по улучшению безопасности удалённого сервера

По результатам анализа (нумерация соответствует найденным рискам):

1. **Анти-брутфорс**: установить **fail2ban** (или sshguard) с фильтром
   `sshd`: ban при 5 неудачных попытках за 10 минут — это точно соответствует
   зафиксированным кампаниям (пик 11–12 попыток в 10-минутном окне);
   дополнительно `MaxAuthTries 4` и `LoginGraceTime 30` уже смягчают перебор
   внутри одного соединения.
2. **Аутентификация по ключам**: перевести `labuser` на SSH-ключи и отключить
   парольную аутентификацию (`PasswordAuthentication no`) — риск № 1
   (подбор пароля «удался») и риск № 6 становятся невозможными; после
   инцидента с входом с 198.51.100.23 пароль в любом случае подлежит замене.
3. **Запрет удалённого root**: `PermitRootLogin no` — на стенде уже
   установлено и подтверждено журналом (57 неудачных попыток под root не
   дают доступа); на продакшн-сервере дополнительно ограничить круг
   пользователей (`AllowUsers labuser`).
4. **Ограничение источников**: разрешить SSH только с доверенных адресов
   (`AllowUsers labuser@<админ-IP>`, firewall/ACL) либо доступ через VPN —
   «интернет-шум» (фоновые подборы с 8 IP) и кампании брутфорса перестанут
   достигать сервиса.
5. **Защита веб-сервера от сканеров**: `limit_req`/`limit_conn` в nginx
   (ограничение частоты с одного IP — всплеск 12–15 запросов за минуты легко
   throttle-ится), WAF (ModSecurity/Coraza с OWASP CRS) против типовых
   эксплойтов, закрытие `/admin` дополнительной аутентификацией и/или
   allowlist-ом адресов.
6. **Сокращение информации о сервере**: `server_tokens off` — сделано и
   подтверждено (в 404-ответах нет версии nginx); не размещать служебные
   файлы в корне сайта, регулярно проверять, что `.env`, `.git`, бэкапы не
   попали в `root` веб-сервера.
7. **Централизация и сохранность журналов**: пересылать access.log/error.log/
   auth.log на отдельный log-сервер (rsyslog/syslog-ng, Loki/ELK) и настроить
   ротацию (logrotate) — при реальной компрометации атакующий первым делом
   чистит локальные журналы; настроить алерты по аномалиям (всплеск 404,
   серия `Failed password`, `Accepted` после серии неудач — именно эта
   связка выявила инцидент).
8. **Верификация ботов**: поисковых роботов проверять по обратному DNS и
   официальным диапазонам адресов (UA «Googlebot» с 198.51.100.77 —
   поддельный), при необходимости ограничивать rate-limit-ом.
9. **Общая гигиена**: регулярные обновления пакетов (unattended-upgrades),
   firewall с политикой «запрещено всё, кроме нужного», IDS/IPS (Suricata,
   Snort) и периодический аудит журналов по методике настоящей работы.

## 6. Вывод

**Семантическая составляющая.** В ходе работы развёрнут «удалённый сервер»
(nginx + OpenSSH в изолированной Docker-сети), настроено полное
журналирование: access.log в кастомном формате с `X-Forwarded-For`, error.log
уровня `warn`, auth.log с syslog-подобными метками времени. Изучены форматы и
семантика записей всех трёх журналов; на массиве данных за 6 дней
(1657 HTTP-запросов от 16 IP, 424 события sshd) освоены типовые приёмы
анализа: агрегация по IP/путям/User-Agent/кодам ответа, профили активности по
часам и выделение всплесков (правило «среднее + 2σ»), сопоставление access.log
и error.log, статистический детект брутфорса по скользящему окну (5 неудач за
10 минут). Воспроизведены и осмыслены характерные паттерны атак: перебор
паролей по словарю пользователей, атака сразу на две подсистемы с одного IP,
маскировка под поискового бота, нормальное «фоновое» сканирование интернета;
показано, как успешный вход после серии неудач служит признаком компрометации
учётной записи, и как запрет входа root нейтрализует перебор главной цели.

**Прагматическая составляющая.** Получен работающий, воспроизводимый
инструмент: команда `./run.sh` поднимает стенд, генерирует трафик и формирует
отчёт анализатора (`demo_output/analysis_report.txt`), пригодный для
регулярного аудита реального сервера — форматы журналов соответствуют
боевым, поэтому анализатор применим к настоящим nginx и sshd после замены
путей к файлам. Сформулированные рекомендации (fail2ban, ключи вместо
паролей, запрет root, rate-limit и WAF, централизация журналов) привязаны к
конкретным найденным фактам и могут быть применены на действующем сервере в
порядке приоритета рисков. Ограничения работы честно задокументированы:
данные первых пяти дней — синтетический backfill с IP из документационных
диапазонов RFC 5737 (для воспроизводимости), а в реальной части внешний адрес
передаётся через `X-Forwarded-For`; на необезличенном стенде анализ
выполняется по тем же алгоритмам без изменений.

### Приложение. Артефакты и воспроизводимость

* запуск: `./run.sh` (docker compose: сборка → web+sshd → backfill → live →
  анализ → сохранение → down);
* журналы за 6 дней: `demo_output/access.log`, `demo_output/error.log`,
  `demo_output/auth.log`;
* транскрипт реальных запросов: `demo_output/live_run.txt` (баннер сервера
  `SSH-2.0-OpenSSH_9.6p1`, ответы curl: страница 200, `/old` 301, скан-путы
  404/403, sshpass: 3 успешных входа, 12 «Permission denied»);
* отчёт анализатора: `demo_output/analysis_report.txt`;
* параметры детекта брутфорса: `--bf-threshold 5`, `--bf-window 10` (мин).
