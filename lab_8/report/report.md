# Отчёт по лабораторной работе №8

## «Управление доступом к приложениям и системам баз данных»

**Вариант:** СУБД MySQL (реляционная СУБД, контейнер `mysql:8.4`).

---

## 1. Постановка задачи

Требуется:

1. Создать программу, которая позволяет установить СУБД (выбранный вариант —
   MySQL).
2. Создать программу, которая позволяет настроить механизм контроля доступа
   для выбранной СУБД.
3. Создать программу для проверки корректности работы настроенной политики
   безопасности СУБД.
4. Создать программу, которая позволяет удалить СУБД, а также созданные ею
   объекты файловой системы.
5. Оформить отчёт о проделанной работе.

Политика безопасности должна быть настроена следующим образом — в системе
должны присутствовать роли:

- **администратор системы** с полным доступом ко всем подсистемам и
  максимальными привилегиями;
- **пользователь** с полными либо частичными правами в подсистеме,
  предоставленными администратором;
- **гость** с правами только на чтение отдельных фрагментов, предоставленных
  администратором.

Дополнительное требование выполнения: всё выполнение — строго внутри Docker
(СУБД — контейнер `mysql:8.4`, клиентские программы — отдельный
контейнер `python:3.12-slim` с драйвером `mysql-connector-python`); порты СУБД
наружу не публикуются (внутренняя сеть compose); на хосте не устанавливается и
не запускается ничего, кроме `docker`/`docker compose`.

## 2. Краткое описание выбранной СУБД

**MySQL 8.4 (LTS)** — одна из наиболее распространённых реляционных СУБД с
открытым исходным кодом. Используется в веб-приложениях, корпоративных и
встраиваемых системах; поддерживает многопользовательский доступ, транзакции
(InnoDB), репликацию.

Механизм контроля доступа MySQL — дискреционный, построен на системе
**привилегий** (privileges), выдаваемых SQL-операторами `GRANT` и отзываемых
`REVOKE`. Привилегии имеют несколько уровней иерархии:

- **глобальный** (`ON *.*`) — на весь сервер (все подсистемы);
- **уровень базы данных** (`ON db.*`);
- **уровень таблицы** (`ON db.table`);
- **уровень колонки** — `GRANT SELECT (col1, col2, ...)` позволяет выдать
  доступ к отдельным колонкам таблицы, не раскрывая остальные;
- **уровень представления** — доступ можно выдавать не к таблице, а к
  представлению (`VIEW`), содержащему только разрешённый «фрагмент» данных.

Учётные записи задаются парой `имя@хост`. Оператор `SHOW GRANTS FOR` выводит
фактически действующие привилегии учётной записи. Специальное право
`WITH GRANT OPTION` позволяет пользователю передавать свои привилегии другим
учётным записям (признак администратора).

В лабораторной работе MySQL развёрнут в контейнере `mysql:8.4` (Docker Compose
проект `lab_8`): данные — в томе `mysql_data`, доступ к серверу — только по
внутренней сети `lab8net` (порты не публикуются). Клиентские программы
выполняются в контейнере-клиенте на базе `python:3.12-slim` с драйвером
`mysql-connector-python` и подключаются к серверу по имени сервиса `mysql`.

Тестовая база данных **`company`** содержит:

- таблицу **`employees`** с колонками разной чувствительности:
  `id`, `name` (неконфиденциальные), `salary` (конфиденциальная),
  `passport_no` (строго конфиденциальная — персональные данные);
- таблицу **`audit_log`** (журнал действий: время, пользователь СУБД, действие);
- представление **`v_public`** (`id`, `name`) — публичный фрагмент `employees`
  для гостевого доступа.

## 3. Описание созданных программ

Все четыре программы находятся в `scripts/`; оркестрация выполняется через
`docker compose`, вся работа с БД — из контейнера-клиента. Полный цикл
демонстрации запускается одной командой `./run.sh`; вывод каждого шага
захватывается в `demo_output/01..05_*.log`.

### 3.1. `install.sh` — установка СУБД

- выполняет `docker compose up -d --build` — поднимает контейнер СУБД
  `lab8-mysql` (`mysql:8.4`) и контейнер-клиент `lab8-client`;
- ожидает готовности СУБД по healthcheck (`mysqladmin ping`, статус
  `healthy`; первая инициализация занимает ~30–60 с);
- применяет `sql/schema.sql` — создаёт БД `company`, таблицы `employees` и
  `audit_log`, наполняет `employees` тестовыми данными (операция
  идемпотентна);
- выводит версию сервера (MySQL 8.4.11) и содержимое `employees` для контроля.

### 3.2. `setup_access.py` — настройка механизма контроля доступа

Программа подключается к серверу от имени `root` и настраивает три роли
согласно методичке.

Сначала создаётся представление `v_public` (публичный фрагмент таблицы
`employees`):

```sql
CREATE OR REPLACE VIEW company.v_public AS SELECT id, name FROM company.employees;
```

Затем создаются учётные записи (`DROP USER IF EXISTS` + `CREATE USER`) и
выдаются привилегии — GRANT-скрипты ролей:

**администратор системы (`admin`)** — полный доступ ко всем подсистемам,
максимальные привилегии:

```sql
GRANT ALL PRIVILEGES ON *.* TO 'admin'@'%' WITH GRANT OPTION;
```

**пользователь (`app_user`)** — частичные права в подсистеме, выданные
администратором; право `DELETE` **не выдаётся**, доступ к колонке
`passport_no` **не выдаётся** (column privileges):

```sql
GRANT SELECT (id, name, salary), INSERT (id, name, salary),
      UPDATE (name, salary) ON company.employees TO 'app_user'@'%';
GRANT SELECT, INSERT ON company.audit_log TO 'app_user'@'%';
```

**гость (`guest`)** — только чтение отдельных фрагментов:

```sql
GRANT SELECT ON company.v_public TO 'guest'@'%';
```

После `FLUSH PRIVILEGES` программа выводит фактические привилегии каждой роли
— `SHOW GRANTS FOR 'admin'@'%' / 'app_user'@'%' / 'guest'@'%'` (полный вывод —
в `demo_output/02_setup_access.log`). Программа идемпотентна: повторный запуск
пересоздаёт учётные записи и заново применяет ту же политику.

Таким образом, чувствительные данные защищены двумя механизмами: для
`app_user` — **привилегиями уровня колонок** (саму таблицу он видит, но
`passport_no` для него «не существует»), для `guest` — **представлением**
(гость вообще не имеет доступа к таблице `employees`, только к фрагменту
`v_public`).

### 3.3. `check_policy.py` — проверка корректности политики безопасности

Программа подключается к серверу от имени всех трёх пользователей (проверяя
тем самым и работоспособность учётных записей) и прогоняет **матрицу из 31
теста**: для каждой роли выполняются попытки `SELECT`, `INSERT`, `UPDATE`,
`DELETE`, DDL (`CREATE TABLE`), чтения запрещённых колонок и операций `GRANT`.
Для каждого теста фиксируется ожидание по политике (`allow`/`deny`) и
фактический результат; расхождение помечается `FAIL`. Успешные DML-операции
откатываются (`rollback`), DDL- и GRANT-пробы удаляются cleanup-командами, поэтому
проверка не изменяет данные. При наличии хотя бы одного `FAIL` программа
завершается с ненулевым кодом возврата (для использования в CI/автоматике).

### 3.4. `uninstall.sh` — удаление СУБД и созданных объектов

Выполняет `docker compose down -v --rmi local --remove-orphans` — останавливает
и удаляет контейнеры `lab8-mysql` и `lab8-client`, внутреннюю сеть, том
`mysql_data` (данные СУБД: БД `company`, учётные записи, привилегии) и локально
собранный образ клиента; затем проверяет и выводит перечень оставшихся
артефактов проекта `lab_8` (по факту — отсутствуют).

## 5. Вывод

**Семантическая составляющая.** В ходе работы изучен и практически применён
встроенный дискреционный механизм управления доступом реляционной СУБД MySQL:
система привилегий с иерархией уровней (сервер → база данных → таблица →
колонка → представление), операторы `GRANT`/`REVOKE`, право `WITH GRANT
OPTION`, учётные записи `user@host` и их инспекция через `SHOW GRANTS`.
Реализован полный жизненный цикл управления доступом: установка СУБД
(контейнеризация Docker Compose, healthcheck), настройка политики безопасности
с тремя ролями методички (администратор — `ALL PRIVILEGES ON *.* WITH GRANT
OPTION`; пользователь — частичные права без `DELETE` и без доступа к колонке
`passport_no` через привилегии уровня колонок; гость — чтение только
представления `v_public`), автоматизированная проверка корректности политики
(матрица 31 теста «ожидание по политике vs факт») и полное удаление СУБД с
всеми созданными объектами. Проверка подтвердила, что построенная политика
работает ровно так, как задано: 31 из 31 проверок пройдено, все запрещённые
операции отклоняются сервером (ошибки 1142/1143), легитимные — выполняются.
Показано, что минимизация привилегий реализуется на разных уровнях:
привилегии уровня колонок скрывают `passport_no` от пользователя,
представление отрезает гостя от таблицы целиком, отсутствие `GRANT OPTION`
не даёт ролям передавать привилегии дальше (эскалация привилегий заблокирована).

**Прагматическая составляющая.** Полученные навыки непосредственно применимы
в промышленной эксплуатации информационных систем. Во-первых, освоенный
подход «принцип наименьших привилегий» (каждая учётная запись получает только
необходимый минимум прав: приложение-пользователь без `DELETE`, сервис-гость
только на представление) — это базовое требование стандартов безопасности
(принцип least privilege из CWE-250/CWE-264, рекомендованный и в источниках к
работе): оно ограничивает ущерб от компрометации учётной записи, уязвимости
приложения или инсайдерских действий. Во-вторых, автоматизация: политика
безопасности описана кодом (идемпотентный `setup_access.py`), а её
корректность проверяется автоматически (`check_policy.py` с ненулевым кодом
возврата при нарушении), что позволяет встраивать проверку политики в CI/CD и
регламенты аудита. В-третьих, контейнеризация: развёртывание/удаление СУБД
одной командой без установки на хост, изоляция портов (доступ к БД только по
внутренней сети compose), пароли через переменные окружения — воспроизводимый
и безопасный способ работы, переносимый на другие СУБД (PostgreSQL, MongoDB) и
другие варианты лабораторной работы. Умение программно управлять привилегиями
и проверять их фактическое состояние необходимо администраторам баз данных,
разработчикам приложений с разграничением доступа и специалистам по
информационной безопасности.
