# Лабораторная работа №12. Совершенствование безопасности удалённых серверов

Вариант IDS/IPS: **Suricata** (образ `jasonish/suricata`, Suricata 8.0.7).

Стенд полностью изолирован в Docker: всё исполнение (сервер, атакующий,
IDS) выполняется внутри контейнеров, порты наружу не публикуются.
На хосте используются только `docker` / `docker compose` и стандартный
`python3` для анализатора (при его отсутствии анализ выполняется внутри
контейнера `attacker`).

## Запуск

```bash
./run.sh
```

Одна команда выполняет весь сценарий:

1. собирает и поднимает стенд (`docker compose up -d --build`, project `lab_12`);
2. **фаза ДО** — IDS отключена, генератор трафика смешивает нормальные
   запросы и атаки; сохраняются только сырые логи (`nginx access.log`,
   `auth.log`);
3. включает движок Suricata (IDS-режим, af-packet; правила ET Open через
   `suricata-update` + собственные `suricata/local.rules`);
4. **фаза ПОСЛЕ** — тот же генератор; собираются `fast.log`/`eve.json`
   с реальными алертами;
5. `analysis/analyze.py` строит сводку `demo_output/before_after.txt`.

Результаты (только реально захваченный вывод) — в `demo_output/`:

```
demo_output/
├── before/                 # фаза ДО
│   ├── attacker_traffic.log   # лог генератора трафика
│   ├── nginx_access.log       # сырой журнал веб-сервера
│   ├── auth.log               # сырой журнал sshd
│   └── fast.log               # пустой: IDS не работала
├── after/                  # фаза ПОСЛЕ (тот же генератор)
│   ├── fast.log               # алерты Suricata (sid, классификация, src/dst)
│   ├── eve.json               # структурированные события (JSON)
│   ├── suricata.log           # журнал движка (загрузка правил и т.д.)
│   ├── stats.log              # статистика движка
│   ├── nginx_access.log, auth.log, nginx_error.log
│   └── attacker_traffic.log
└── before_after.txt        # сводка анализа ДО/ПОСЛЕ
```

Требование интернета: при сборке образов (`apt-get`) и загрузке набора
правил ET Open (`suricata-update`). Если репозиторий правил недоступен,
стенд продолжает работать на собственных правилах `suricata/local.rules`
(в `after/suricata.log` это видно честно).

## Топология и способ перехвата трафика

Проблема: в обычной bridge-сети Docker трафик «контейнер-контейнер»
коммутируется на L2 и **не виден** третьему контейнеру той же сети
(даже с af-packet/promisc) — мост не зеркалирует кадры между veth.

Поэтому используется маршрутизируемая топология с Suricata в роли
L3-шлюза между двумя сетями compose:

```
            сеть "outside" (172.28.100.0/24)          сеть "secure" (172.29.100.0/24)

  ┌──────────────┐   ip route -> .3   ┌──────────────────┐   ip route -> .3   ┌────────────────┐
  │   attacker   │-------------------)|     suricata     |((-------------------│  web (server)  │
  │ 172.28.100.20|     eth0           | .3        .3     |           eth0     | 172.29.100.10  │
  │ curl/nmap/ssh│                    | ip_forward=1     |                    │ nginx + sshd   │
  └──────────────┘                    | af-packet: eth0  |                    └────────────────┘
                                      | IDS-режим        |
                                      └──────────────────┘
```

* `attacker` направляет маршрут до сети `secure` через IP Suricata
  (`ip route replace 172.29.100.0/24 via 172.28.100.3`);
* `web` симметрично направляет маршрут до сети `outside` через Suricata
  (`via 172.29.100.3`), чтобы ответы шли обратно через точку анализа;
* контейнер `suricata` (`cap_add: NET_ADMIN, NET_RAW`,
  `sysctls: net.ipv4.ip_forward=1`) пересылает пакеты между сетями;
  весь трафик `attacker <-> web` в обоих направлениях проходит через
  его outside-интерфейс `eth0`, где перехватывается `af-packet`.

Так как обе подсети закреплены в compose (`172.28.100.0/24` = external,
`172.29.100.0/24` = защищаемая), в конфиге Suricata корректно заданы
`HOME_NET: [172.29.100.0/24]`, `EXTERNAL_NET: !$HOME_NET` — публичные
правила ET Open матчатся со стороны атакующего.

Режим работы Suricata — **IDS** (обнаружение): движок ничего не
блокирует, поэтому в фазе ПОСЛЕ запросы по-прежнему доходят до nginx
(это видно в `after/nginx_access.log`), но каждое событие получает
алерт в `fast.log`/`eve.json`. Перевод в IPS (inline drop) возможен на
этой же топологии (nfqueue/af-packet ips mode с copy-mode), в работе не
используется.

Фаза ДО отличается от фазы ПОСЛЕ только состоянием движка обнаружения:
путь пакета один и тот же (Suricata-контейнер работает шлюзом и в фазе
ДО — иначе трафик не пошёл бы), но движок не запущен, правил нет,
алертов нет. Это соответствует ситуации «сервер без IDS»: факты атак
существуют лишь пост-фактум в сырых логах служб.

## Состав стенда

| Сервис    | Образ                      | Назначение |
|-----------|----------------------------|------------|
| `suricata`| `jasonish/suricata:latest` (8.0.7) | L3-шлюз стенда + IDS-движок (af-packet на eth0) |
| `web`     | сборка `server/` (debian + nginx + openssh-server) | защищаемый сервер: HTTP:80, SSH:22 |
| `attacker`| сборка `attacker/` (python + curl + nmap + sshpass) | генератор нормального и атакующего трафика |

Генератор (`attacker/traffic_gen.py`) воспроизводит:

* нормальные запросы (страницы, статика, API);
* path traversal к `/etc/passwd` (в т.ч. URL-encoded);
* SQL-инъекции в query string (UNION SELECT, тавтологии, комментарии);
* зондирование чувствительных путей (`.env`, `/admin`, `wp-login.php`…);
* SYN-сканирование портов `nmap -sS`;
* брутфорс SSH (`sshpass` + `ssh`, разные пользователи/пароли).

Анализатор (`analysis/analyze.py`) сравнивает фазы, считает алерты по
правилам, строит разбивку по классификациям и топ источников, пишет
`demo_output/before_after.txt`.

## Структура репозитория

```
lab_12/
├── run.sh                  # единственная точка входа
├── docker-compose.yml      # сети outside/secure, проект lab_12
├── suricata/
│   ├── entrypoint.sh       # режимы gateway (фаза ДО) / ids (движок)
│   ├── genconf.py          # генерация suricata.yaml (HOME_NET, af-packet, выводы)
│   └── local.rules         # собственные правила: traversal, SQLi, scan, SSH
├── server/                 # Dockerfile + nginx-конфиг + start.sh (nginx, sshd)
├── attacker/               # Dockerfile + setup.sh + traffic_gen.py
├── analysis/analyze.py     # сводка ДО/ПОСЛЕ
├── demo_output/            # только реально захваченный вывод
├── data/suricata/          # рабочие логи движка (создаётся при запуске)
├── report/report.md        # отчёт по лабораторной работе
└── README.md
```

## Известные особенности

* В Suricata 8.0.7 (образ `jasonish/suricata`) запуск без явного
  аргумента захвата печатает usage — интерфейс задаётся и в конфиге,
  и в командной строке (`--af-packet=eth0`); конфиг генерируется из
  штатного `suricata.yaml` образа скриптом `suricata/genconf.py`.
* Кадры LLDP/STP от docker-моста порождают шумовые события
  `SURICATA Ethertype unknown` — сигнатура `2200121` подавлена в
  `threshold.config` (генерируется в `suricata/entrypoint.sh`).
* Порты стенда наружу не публикуются; трафик не покидает docker.
