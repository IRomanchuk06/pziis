## 1. Постановка задачи

Удалённый сервер, доступный из сети (веб-приложение и служба SSH),
подвержен типовым сетевым атакам: попыткам чтения файлов через path
traversal, SQL-инъекциям в параметрах запросов, зондированию
чувствительных путей, сканированию портов и подбору паролей SSH.
Журналы самих служб (nginx, sshd) фиксируют только факты обращений, но
не классифицируют их: администратор не получает ни сигналов о попытках
вторжения, ни агрегированной картины.

**Цель работы** — установить и настроить систему обнаружения/предотвращения
вторжений (вариант — **Suricata**), обеспечивающую автоматизированный
анализ сетевого трафика и событий, и продемонстрировать её эффект
сравнением одного и того же профиля трафика «до» и «после» включения
защиты.

Задачи:

1. установить Suricata и настроить её в режиме IDS (af-packet) на
   интерфейсе сети защищаемого сервера; настроить `HOME_NET`,
   подключить набор правил ET Open и собственные правила;
2. реализовать генератор трафика: смесь легитимных запросов и атак
   (path traversal к `/etc/passwd`, SQL-инъекции в query string,
   зондирование чувствительных путей, SYN-сканирование портов `nmap`,
   брутфорс SSH);
3. снять сценарий **ДО** (IDS отключена): убедиться, что атаки видны
   только пост-фактум в сырых журналах служб;
4. снять сценарий **ПОСЛЕ** (IDS включена): получить реальные алерты с
   идентификаторами сигнатур, классификацией и адресами сторон;
5. проанализировать журналы подсистем и файлов, оформить отчёт.

Стенд целиком развёрнут в Docker (docker compose, проект `lab_12`):
контейнеры `attacker` (генератор: python, curl, nmap, sshpass),
`web` (защищаемый сервер: nginx + OpenSSH) и `suricata` (IDS-шлюз).
Порты наружу не публикуются.

## 2. Описание установленного программного обеспечения

### 2.1. Назначение

**Suricata** (OISF, версия 8.0.7) — высокопроизводительная система
обнаружения вторжений (IDS) / предотвращения вторжений (IPS) и движок
анализа сетевой безопасности (Network Security Monitoring). Suricata
перехватывает сетевой трафик, декодирует протоколы, сопоставляет его с
базой сигнатур и событийных правил и формирует оповещения и
структурированные журналы; в режиме IPS способна блокировать трафик
(deny, drop, reject).

### 2.2. Режимы работы

| Режим | Механизм | Суть |
|---|---|---|
| **IDS (обнаружение)** | af-packet / pcap, копия трафика | Пакеты только анализируются; атака не блокируется, но фиксируется |
| **IPS (предотвращение)** | nfqueue, af-packet в inline-режиме (`copy-mode: ips`) | Движок получает пакет до доставки и решает: пропустить (accept) или отбросить (drop) |
| **NSM/журналирование** | eve.json | Полный разбор протоколов: HTTP, TLS, DNS, SSH, файлы, потоки |
| Захват с NIC | **af-packet** (zero-copy, tpacket_v3, PF_PACKET fanout), **af-xdp**, **dpdk**, pcap | Способы получения пакетов с сетевого интерфейса; af-packet — основной на Linux, поддерживает зеркалирование (SPAN) и inline |

В работе используется **IDS-режим с af-packet** на outside-интерфейсе
контейнера-шлюза (см. п. 5.1).

### 2.3. Комплекс решаемых задач

* сигнатурный анализ трафика в реальном времени (десятки тысяч правил);
* обнаружение эксплойтов, сканирования, брутфорса, вредоносных URL,
  утечек учётных данных;
* протокольный анализ и журналирование (HTTP, TLS/JA3, DNS, SSH, SMB…);
* статистика потоков и производительности;
* интеграция с SIEM (вывод eve.json/Elastic), Suricata unix-socket
  управление, правила Emerging Threats (ET Open/ET Pro);
* в режиме IPS — блокировка хостов/потоков, сброс соединений (reject).

### 2.4. Принцип работы (движки распознавания и правила)

Конвейер обработки пакета: **захват (af-packet) → декодеры
(eth/IP/TCP/UDP) → дефрагментация IP → потоковый движок (stream engine:
отслеживание TCP-сессий, реконструкция сегментов) → разбор прикладного
уровня (app-layer парсеры: libhtp для HTTP, Rust-парсеры TLS/DNS/SSH) →
детектирующий движок (detect engine)**.

Ядро детектирования — **мультитшаблонный поиск (MPM, multi-pattern
matching)**: префильтр Hyperscan/Aho-Corasick за один проход находит
кандидатов среди всех `content`-строк базы правил, после чего
применяются точные проверки оставшихся опций (pcre, пороги,
sticky-buffers). Правила используют домены (`http.uri`, `http.user_agent`
и т. п.), что исключает ложные срабатывания на «похожих» пакетах других
протоколов.

Формат правила (синтаксис Snort):

```
alert http $EXTERNAL_NET any -> $HTTP_SERVERS $HTTP_PORTS (
  msg:"LOCAL WEB-TRAVERSAL обращение к /etc/passwd в URI";
  flow:established,to_server; http.uri.raw; content:"/etc/passwd";
  nocase; classtype:web-application-attack; sid:1000001; rev:1;)
```

Поля: действие (`alert`), протокол, источники/приёмники (с использованием
переменных `HOME_NET`/`EXTERNAL_NET`), опции (содержание, буферы, PCRE,
пороги `detection_filter`) и идентификация (`sid`, `rev`,
`classtype` — категория для классификатора).

В работе подключены два файла правил: публичный набор **ET Open**
(`suricata-update`, ~53 000 правил после сборки; загрузчик выполнялся
внутри контейнера) и собственные **`local.rules`** (8 сигнатур:
path traversal, SQL-инъекции, зондирование путей, пороги для
сканирования портов и SSH-брутфорса). Итог: `53106 rules successfully
loaded, 0 rules failed` (after/suricata.log).

## 3. Краткое описание анализируемых подсистем

**nginx** — веб-сервер/reverse-proxy защищаемого сервера (порт 80).
Обслуживает статические страницы, `/api/status`; все входящие запросы
записывает в `access.log` (метод, URI, код ответа, User-Agent, IP
клиента), ошибки — в `error.log`. nginx сам по себе не различает
«обычный» и «атакующий» запрос: коды 400/404 лишь косвенно указывают
на нестандартную активность.

**OpenSSH (sshd)** — служба удалённого администрирования (порт 22).
При авторизации по паролю пишет в `auth.log` события `Failed password`,
`Invalid user`, `Accepted password`. Классическая цель брутфорса:
служба обязана принимать подключения из сети, а один неудачный вход
ничем не отличается от опечатки пользователя — вредоносную
активность показывает только статистика (много отказов с одного IP).

Обе подсистемы находятся в сети `secure` (172.29.100.0/24, это
`HOME_NET`); атакующий — в сети `outside` (172.28.100.0/24,
`EXTERNAL_NET`). Межсетевой путь проходит через контейнер с Suricata,
работающий шлюзом (`ip_forward=1`), поэтому IDS видит весь трафик
`attacker ↔ web` в обоих направлениях.

## 4. Краткое описание анализируемых файлов

| Файл | Что содержит | Зачем нужен |
|---|---|---|
| `nginx_access.log` | по строке на HTTP-запрос: IP, время, `«GET /uri HTTP/1.1»`, код ответа, размер, Referer, User-Agent | Аудит обращений к веб-серверу «пост-фактум»; в фазе ДО — единственное свидетельство атак |
| `auth.log` | события sshd: `Failed password for root from 172.28.100.20 port 34952 ssh2` и т. п. | Аудит попыток входа; основа ручного выявления брутфорса |
| `suricata/fast.log` | по строке на алерт: время, `[gid:sid:rev]`, текст сигнатуры, классификация, приоритет, `{прото} src -> dst` | Быстрое человекочитаемое оповещение «что, кто, куда» |
| `suricata/eve.json` | JSON-события: `alert` (sid, категория, severity), `http` (url, UA, код), `flow`, `stats` | Машиночитаемый журнал для SIEM/анализаторов; объединяет алерты с метаданными запроса и потока |
| `suricata/suricata.log` | журнал самого движка: загрузка правил (`53106 rules successfully loaded`), запуск потоков | Контроль работоспособности IDS |
| `suricata/stats.log` | периодическая статистика (пакеты, потоки, память) | Мониторинг производительности движка |

Пример строки `fast.log` (реальный, из `after/fast.log`):

```
10/05/2026-12:50:22.194767  [**] [1:1000001:1] LOCAL WEB-TRAVERSAL обращение
к /etc/passwd в URI [**] [Classification: Web Application Attack]
[Priority: 1] {TCP} 172.28.100.20:49538 -> 172.29.100.10:80
```

То же событие в `eve.json` содержит, кроме сигнатуры, разобранный
запрос: `http.url = /../../etc/passwd`, `status = 400`, User-Agent,
параметры потока.

## 5. Анализ запросов «до» и «после» настройки политики безопасности

### 5.1. Топология перехвата

В bridge-сети Docker трафик «контейнер–контейнер» коммутируется на L2 и
стороннему контейнеру не виден. Поэтому Suricata включена как
**L3-шлюз** между двумя сетями compose: `attacker` маршрутизирует
трафик к `secure` через IP Suricata, `web` отвечает симметрично через
него же. Движок слушает outside-интерфейс (`af-packet`, 1 поток,
`cluster_flow`), т. е. каждый пакет атаки проходит через точку анализа
в обоих направлениях. Путь пакета одинаков в обеих фазах; фазы
различаются только состоянием движка обнаружения.

## 6*. Сравнение Suricata с аналогами

| Критерий | **Suricata** | Snort | OSSEC (Wazuh) | Zeek (Bro) | Tripwire |
|---|---|---|---|---|---|
| Класс | NIDS/NIPS + NSM | NIDS/NIPS | HIDS | Анализатор сетевой телеметрии | HIDS (целостность файлов) |
| Объект анализа | Сетевой трафик | Сетевой трафик | Логи хоста, файловая система, реестр | Сетевой трафик (высокоуровневые сценарии) | Файлы хоста |
| Метод | Сигнатуры + MPM-префильтр, протокольные буферы, пороги | Сигнатуры (родоначальник формата) | Правила корреляции логов, целостность | Сценарные политики (Tcl-подобный язык), извлечение «сведений» | Хэши/атрибуты файлов против эталонной БД |
| Блокировка (IPS) | Да (nfqueue/inline) | Да (Snort inline) | Нет (только алерты) | Нет (по умолчанию) | Нет |
| Многопоточность/GPU | Да (workers, Hyperscan; аппаратное ускорение) | Ограниченно (однопоточный в ядре 2.x, Snort 3 многопоточный) | Да | Да | Нет |
| Типовое применение | Шлюз/зеркало сети, пограничная защита | Малые/средние сети, совместимость правил | Защита конкретного сервера/эндпоинта | Научно-исследовательский и forensic-анализ трафика | Контроль неизменности системных файлов |

Вывод по сравнению: Suricata перекрывает нишу Snort (тот же формат
правил, ET/Snort-правила совместимы) и выигрывает у него в
производительности на многоядерных системах; OSSEC и Tripwire решают
другую задачу (хост-уровень) и применяются вместе с NIDS; Zeek мощнее в
глубоком исследовании трафика, но не даёт «из коробки» сигнатурных
алертов и IPS-функций. Для задачи защиты удалённого сервера от сетевых
атак Suricata — наиболее сбалансированный выбор.

## 7. Вывод

**Семантическая составляющая.** В работе изучены принципы построения
систем обнаружения/предотвращения вторжений и освоена Suricata 8:
развёрнут стенд «атакующий — IDS-шлюз — защищаемый сервер», движок
настроен в режиме IDS с захватом af-packet, настроены переменные
`HOME_NET`/`EXTERNAL_NET`, подключены набор ET Open (53 106 правил) и
собственные сигнатуры. Показан принцип работы сигнатурного детектирования:
декодирование протоколов → потоковая реконструкция → прикладной разбор
(HTTP) → мультитшаблонный префильтр → точные проверки правил → алерт.
Экспериментально подтверждено, что без IDS атаки (path traversal,
SQL-инъекции, зондирование путей, сканирование портов, брутфорс SSH)
существуют только как «сырые» записи в access.log/auth.log, а с
включённой Suricata тот же трафик порождает 134 алерта 16 сигнатур с
классификацией, приоритетом и однозначной идентификацией источника
(172.28.100.20). Зафиксировано принципиальное различие режимов: IDS
обнаруживает (запросы доходят до nginx и в фазе ПОСЛЕ), IPS —
предотвращает.

**Прагматическая составляющая.** Получен воспроизводимый инструмент
(`./run.sh`), который поднимает изолированный стенд, выполняет обе фазы
и строит сводку «до/после» (demo_output/before_after.txt) — его можно
переиспользовать для обучения и регрессионной проверки правил.
Практическая ценность для эксплуатации сервера: Suricata даёт
оператору мгновенные оповещения вместо ручного просмотра журналов,
структурированный журнал eve.json пригоден для передачи в SIEM и
автоматического реагирования (блокировка по iprep, переход в IPS-режим
на той же топологии), а накопленная статистика позволяет количественно
оценивать интенсивность атак. Ограничения, выявленные в работе:
сигнатурный подход требует актуального набора правил и не ловит
неизвестные атаки; пороговые правила шумят (94 алерта на один nmap-скан)
и нуждаются в настройке; IDS без IPS не уменьшает количество
достигающих сервера запросов — она сокращает время их обнаружения.
Направления развития: перевод стенда в inline-режим с демонстрацией
drop, корреляция алертов Suricata с auth.log (например, средствами
Wazuh), тонкая настройка порогов и подключение репозитория ET Pro.
