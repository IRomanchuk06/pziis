# 1. Постановка задачи

Требуется создать программу, которая позволяет настроить список контроля
доступа (ACL) для объектов файловой системы Linux и проверить корректность
её работы, а именно:

1. Создать группы пользователей `group_iit1`, `group_iit2`.
2. Создать пользователей `iit11`, `iit12` и добавить их в группу `group_iit1`.
3. Создать пользователей `iit21`, `iit22` и добавить их в группу `group_iit2`.
4. Предоставить пользователю `iit21` административные привилегии.
5. Создать пользователя `iit3`.
6. Создать папку `pzs`.
7–11. Создать в ней подпапки с правами чтения/записи/выполнения:
   `pzs11` — только для владельца; `pzs12` — только для группы;
   `pzs13` — только для остальных пользователей; `pzs14` — для всех
   пользователей; `pzs15` — только для администратора (root).
12. Сменить текущего пользователя на `iit11`.
13. В папках `pzs11`–`pzs14` создать файлы `file11`–`file55` со всеми
    комбинациями прав (чтение / запись / выполнение) для классов
    «владелец», «группа group_iit1», «остальные», «все пользователи»,
    «администратор». Файлы по шаблону `filex5` (file15, file25, file35,
    file45, file55) содержат текст `read testVariable`, остальные —
    `echo "Hello World"`.
14. Для каждого из созданных файлов проверить, можно ли его прочитать,
    отредактировать и запустить от имени `iit11`, `iit12`, `iit21`, `iit22`,
    `iit3` и суперпользователя (root).
15. Запустить каждый файл шаблона `filex5` пользователем `iit11` и проверить,
    можно ли остановить запущенный процесс пользователями `iit11`, `iit12`,
    `iit21`, `iit22`, `iit3` и root.
16. В каждой из созданных папок проверить от имени разных пользователей:
    чтение содержимого папки, создание нового файла, удаление существующих
    файлов.
17. Удалить созданные файлы, папки, пользователей `iit11`, `iit12`, `iit21`,
    `iit22`, `iit3` и группы `group_iit1`, `group_iit2`.

Дополнительно (по требованиям к отчёту): описать программу и результаты,
сделать вывод с семантической и прагматической составляющими.

# 2. Описание созданной программы

## 2.1. Среда выполнения

Программа выполнена на языке **Bash** и запускается внутри контейнера
**Docker** на базе образа `ubuntu:24.04` (обычный `docker run` через
Compose, без `--privileged`; внутри контейнера сценарии администрирования
работают от root — это штатная роль установщика системы). На хосте ничего,
кроме Docker/Compose, не используется. Такой подход даёт полностью
воспроизводимый и изолированный эксперимент: вся система (пользователи,
группы, sudoers, файлы) создаётся «с нуля» при каждом запуске и полностью
удаляется при очистке.

Состав решения:

```
lab_10/
├── run.sh                   — одна команда: сборка образа + запуск контейнера
│                              + сохранение всего вывода
├── Dockerfile               — ubuntu:24.04 + пакеты sudo и procps
├── docker-compose.yml       — compose-проект lab_10, bind-mount ./demo_output
├── scripts/
│   ├── run_demo.sh          — оркестратор: выполняет шаги 1–17 задания
│   ├── common.sh            — общие константы (субъекты, объекты) и функции
│   ├── setup.sh             — шаги 1–11
│   ├── create_files.sh      — шаги 12–13 (+ inner_create.sh,
│   │                           inner_create_root.sh)
│   ├── check_matrix.sh      — шаг 14 (+ inner_matrix.sh)
│   ├── process_control.sh   — шаг 15
│   ├── check_dirs.sh        — шаг 16 (+ inner_dirs.sh)
│   └── cleanup.sh           — шаг 17
├── demo_output/             — только реально захваченный вывод прогона:
│   ├── run_full.log         — полный журнал (весь stdout контейнера)
│   ├── matrix.txt           — матрица доступа шага 14
│   ├── matrix_detail.txt    — журнал каждой из 1800 проверок
```

Смена пользователя во всех проверках выполняется штатным способом:
`su - <пользователь> -s /bin/bash -c '<команда>'` (из-под root пароль не
требуется; `-m -s /bin/bash` при создании гарантирует рабочий shell и
домашний каталог). Все проверки — реальные команды: чтение `cat`,
редактирование `echo >>`, запуск `./файл`, `ls`, `touch`, `rm`, `kill`.

## 2.2. Ключевые проектные решения

**а) Основная группа пользователей.** Пользователи созданы с основной
группой `group_iit1`/`group_iit2` (`useradd -g ...`). Это необходимо, чтобы
файлы, созданные `iit11`, имели группу-владельца `group_iit1` и сценарии
«права только для группы» были осмысленными:

```bash
useradd -m -s /bin/bash -g group_iit1 iit11
useradd -m -s /bin/bash -g group_iit1 iit12
useradd -m -s /bin/bash -g group_iit2 iit21
useradd -m -s /bin/bash -g group_iit2 iit22
useradd -m -s /bin/bash iit3
```

**б) Административные привилегии `iit21`** — членство в группе `sudo` и
правило `NOPASSWD` (в контейнере у учётных записей нет паролей):

```bash
usermod -aG sudo iit21
echo 'iit21 ALL=(ALL) NOPASSWD: ALL' > /etc/sudoers.d/iit21
chmod 440 /etc/sudoers.d/iit21
visudo -c   # /etc/sudoers.d/iit21: parsed OK
```

**в) Владельцы папок `pzs11`–`pzs15`.** Задание фиксирует только права,
поэтому владельцы выбраны так, чтобы смысл каждой папки был достижим с
учётом порядка проверки ACE в Linux (владелец → группа → остальные;
процессу применяется только первый совпавший класс):

| папка | права | владелец:группа | кто реально получает R/W/X |
|-------|-------|-----------------|-----------------------------|
| pzs11 | `700` | `iit11:group_iit1` | только владелец `iit11` (+root) |
| pzs12 | `070` | `root:group_iit1` | только члены группы `group_iit1` (iit11, iit12) (+root) |
| pzs13 | `007` | `root:root` | только «остальные» — все обычные пользователи (+root) |
| pzs14 | `777` | `iit11:group_iit1` | все пользователи |
| pzs15 | `700` | `root:root` | только root |

Если бы `pzs12` (070) принадлежала `iit11`, то `iit11` как владелец
получил бы отказ (владельцу применяются только биты владельца, а они нулевые)
и не смог бы выполнить шаг 13 — создать файлы. Назначение владельцем root
переводит `iit11` в класс «группа», что и требуется. Аналогично для
`pzs13` (007): владелец и группа root делают «остальными» всех обычных
пользователей.

**г) Точные права файлов (шаг 13).** Файлы `file11`–`file45` создаёт
`iit11` (скрипт `inner_create.sh`), `file51`–`file55` («только для
администратора») — `iit21` через `sudo`, владелец `root:root`
(скрипт `inner_create_root.sh`):

```bash
declare -A PERMS=(
  [file11]=400 [file12]=600 [file13]=200 [file14]=700 [file15]=100
  [file21]=040 [file22]=060 [file23]=020 [file24]=070 [file25]=010
  [file31]=004 [file32]=006 [file33]=002 [file34]=007 [file35]=001
  [file41]=444 [file42]=666 [file43]=222 [file44]=777 [file45]=111
)
case "$f" in
  file15|file25|file35|file45) printf '#!/bin/bash\nread testVariable\n' > "$f" ;;
  *)                           printf '#!/bin/bash\necho "Hello World"\n' > "$f" ;;
esac
chmod "${PERMS[$f]}" "$f"
```

Во все файлы добавлена строка `#!/bin/bash` — без неё запуск `./файл` в
Linux невозможен в принципе (файл без интерпретатора не является
исполняемым сценарием).

**д) Запуск `filex5` в шаге 15 (обход ограничения самого задания).**
Файлы `filex5` имеют права «только выполнение» (100/010/001/111), а в
Linux интерпретатор `#!/bin/bash` обязан открыть файл на чтение, поэтому
прямой запуск `./filex5` невозможен ни для одного пользователя, включая
`iit11` (это зафиксировано в результатах). Чтобы всё же получить реальный
процесс пользователя `iit11`, выполняющий текст файла и «висящий» на
`read testVariable`, используется механизм наследования дескрипторов:
root читает файл (root имеет право чтения) и передаёт его текст в FIFO;
stdin процесса `bash -s`, запущенного от имени `iit11` через `su`,
подключён к этому FIFO:

```bash
mkfifo "$FIFO"; exec 9<>"$FIFO"       # держим FIFO открытым (нет EOF)
cat "$dir/$file" >&9 &                # root читает файл и пишет текст в FIFO
su - iit11 -s /bin/bash -c 'exec bash -s' <"$FIFO" >/dev/null 2>&1 &
PID=$(pgrep -u iit11 -x bash | head -1)   # su порождает дочерний процесс
```

Это демонстрирует важнейший принцип DAC: **проверка прав выполняется в
момент открытия файла (open)**, а чтение из уже открытого (унаследованного)
дескриптора прав не проверяет. Процесс принадлежит `iit11`, что и требуется
для проверки `kill`.

- автоматическая проверка матрицы доступа (1800 реальных команд) с

### Объяснение результатов по модели прав Linux

1. **Класс определяется первым совпавшим ACE: владелец → группа → остальные.**
   Самые показательные строки — `file21`–`file25` («только для группы»):
   *владелец* `iit11` получил полный отказ (`file21`: `iit11` — `---`,
   `iit12` — `+--`), потому что `iit11` попадает в класс «владелец», которому
   применяются только биты владельца (0), а групповые биты к нему уже не
   применяются. Зеркально для `file31`–`file35` («только для остальных»):
   доступ имеют `iit21`, `iit22`, `iit3`, а `iit11` (владелец) и `iit12`
   (группа) — нет.

2. **Право записи не предполагает право чтения.** `file13` (200) и `file43`
   (222): владелец/пользователи могут дозаписывать (`-+-`), но не могут
   прочитать файл (`cat` открывает файл только на чтение — отказ). Именно
   поэтому проверка «редактирование» реализована как `echo >> файл`.

3. **Сценарий «только выполнение» нельзя выполнить.** Для `file15`, `file25`,
   `file35`, `file45` запуск запрещён всем, кроме root: ядро выполняет
   `execve` (бит x есть), но интерпретатор `/bin/bash` обязан открыть
   сценарий на чтение и получает `Permission denied` (код возврата 126).
   root читает файл с обходом DAC (`CAP_DAC_OVERRIDE`), поэтому выполняет
   и их (`+++`).

4. **root подчиняется не всем правилам.** Чтение и запись root разрешены
   всегда (DAC override), но для **выполнения** файла необходимо, чтобы
   хотя бы один бит x в правах был установлен: файлы без единого бита x
   (например `file11` 400, `file42` 666) root выполнить не может (`++-`).
   Запуск разрешён ровно для 10 файлов с x-битами: file14, file15, file24,
   file25, file34, file35, file44, file45, file54, file55.

5. **«Только для администратора»** (`file51`–`file55`, root:root): все
   обычные пользователи получают отказ по всем операциям; при этом
   `iit21` как администратор получает доступ через sudo (проверено
   дополнительно: `sudo cat file51` → OK, `sudo ls pzs15` → OK, напрямую —
   DENIED). Это практическое подтверждение шага 4 задания.

6. **Каталог: нужен бит `x` на каждом элементе пути.** Отказы в `pzs11`/`pzs12`
   для «посторонних» пользователей возникают ещё до проверки прав самого
   файла: без `x` на каталоге путь к файлу не разрешается.

## 3.3. Управление процессами (шаг 15)

Каждый из 20 файлов `filex5` (5 файлов × 4 каталога) запускался как процесс
пользователя `iit11` (висит на `read testVariable`), после чего каждый
субъект пытался остановить свежезапущенный процесс командой `kill`. Всего
120 попыток + 20 попыток `iit21` через sudo. Итог:

| субъект | результат |
|---------|-----------|
| iit11 (владелец процесса) | **OK** — 20/20, процесс завершается |
| iit12 | DENIED — 20/20, `Operation not permitted` |
| iit21 (напрямую) | DENIED — 20/20, `Operation not permitted` |
| iit21 (через sudo) | **OK** — 20/20 (административные привилегии) |
| iit22 | DENIED — 20/20 |
| iit3 | DENIED — 20/20 |
| root | **OK** — 20/20 |

Прямой запуск `./filex5` от `iit11` при этом также зафиксирован: DENIED,
rc=126 (`Permission denied`) — см. пояснение в п. 3(3); показательно, что
для `file15`/`file45` (бит x у владельца/группы/всех) ошибку выдаёт уже
интерпретатор `/bin/bash`, а для `file25`/`file35` (у владельца битов нет) —
сам execve: ядро отклоняет попытку раньше.

Семантика сигналов: процессу может послать сигнал только владелец процесса
(тот же UID) или суперпользователь; принадлежность к какой-либо группе на
это не влияет.

## 3.4. Операции над папками (шаг 16)

Для каждой папки и каждого субъекта (после каждого субъекта папка
восстанавливалась из копии) выполнены: `ls` (чтение содержимого), `touch`
(создание файла), `rm` каждого из 26 файлов (25 файлов + созданный). Итог:
**54 операции разрешено, 36 запрещено** (6 субъектов × 5 папок × 3 операции).

| папка | ls / touch / rm |
|-------|-----------------|
| pzs11 (700, iit11) | только iit11 и root; остальные — отказ во всех операциях |
| pzs12 (070, root:group_iit1) | только iit11, iit12 и root |
| pzs13 (007, root:root) | все пользователи и root |
| pzs14 (777) | все пользователи и root |
| pzs15 (700, root:root) | только root; root удаляет созданный им файл (1 OK), остальных 25 файлов в папке нет |

Ключевые наблюдения:

- право **удалять** файл определяется правами на **каталог** (w+x), а не
  правами самого файла: в `pzs14` (777, без sticky-бита) любой пользователь
  успешно удалял чужие файлы, включая файлы с правами 400, и файлы,
  принадлежащие root (создание/удаление `root:root`-файлов в pzs14
  выполнялось root);
- для чтения содержимого (`ls`) нужен бит `r` каталога, для входа и создания/
  удаления — бит `x`; в `pzs11` (700) «посторонним» недоступно даже `ls`,
  хотя имена файлов известны;
- в `pzs15` root создаёт и удаляет файлы свободно, все остальные получают
  `Permission denied` уже на `ls`.

# 4. Вывод

**Семантическая составляющая.** В работе исследована классическая модель
избирательного управления доступом (DAC) файловой системы Linux как частный
случай ACL: каждый объект несёт ACL из трёх обязательных ACE (владелец,
группа-владелец, остальные), а решение о доступе принимается по первому
совпавшему классу — это подтверждено экспериментально «парадоксальными»
строками матрицы: владелец файла с правами «только для группы» получает
отказ (file21–file25 для iit11), владелец файла 200 не может его прочитать,
но может дописать. Биты r/w/x интерпретируются по-разному для файлов и
каталогов (чтение каталога — имена, выполнение — проход по пути, запись —
создание/удаление объектов), проверка прав выполняется на всём пути, а
право удаления определяется каталогом (отсутствие sticky-бита в 777
позволяет удалять чужие файлы). Права суперпользователя ограничены только
частично: root обходит DAC при чтении/записи, но для выполнения файла
необходим хотя бы один бит x; для интерпретируемых сценариев обычному
пользователю дополнительно требуется право чтения — «execute-only» сценарий
исполнить нельзя (интерпретатор обязан открыть файл на чтение), тогда как
root читает файл с обходом DAC и выполняет его.
Модель распространяется и на процессы: сигнал может отправить
только владелец процесса или root, административные привилегии (sudo)
расширяют возможности пользователя до суперпользователя точечно и
контролируемо. Наконец, проверка прав происходит при открытии объекта:
унаследованный дескриптор (FIFO в шаге 15) позволяет продолжить работу с
файлом без повторных проверок — принцип, на котором строятся и уязвимости
типа TOCTOU, и легитимные механизмы передачи доступа.

**Прагматическая составляющая.** Получен практический навык
администрирования доступа в Linux: создание групп и пользователей с заданными
основными группами, назначение прав командами chmod/chown в символьном и
восьмеричном виде, настройка административных привилегий через sudoers,
диагностика отказов по сообщениям `Permission denied` и кодам возврата
(126/127), проверка доступа реальными командами от имени разных
пользователей через `su`. Разработанная программа автоматизирует полный
цикл: развёртывание стенда → 1800 автоматизированных проверок файлов →
120+20 проверок управления процессами → 90 проверок каталогов →
гарантированная очистка; все результаты воспроизводимы одной командой
`./run.sh` в изолированном контейнере Docker и сохраняются в виде журналов и
таблиц, пригодных для аудита. Такой стенд может использоваться для
обучения, регрессионной проверки политик доступа и демонстрации типовых
ошибок назначения прав (чрезмерно широкие права каталогов, отсутствие
sticky-бита на общих каталогах, «запись без чтения», иллюзия защиты
«execute-only»-сценариев). Практическая ценность подтверждена: итоги
автоматических проверок полностью совпали с теоретической моделью прав
Linux (422/1378 для файлов; 40 OK / 80 DENIED + 20 успешных sudo-остановок
для процессов; 54/36 для каталогов).
